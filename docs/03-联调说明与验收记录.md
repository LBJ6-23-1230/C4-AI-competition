### 🟠 缺陷：`Content-Type` 带 `charset` 时中文消息会被丢掉（已加固）

**发现过程**：用工程自带的 `tools/run_backend_core_regression.ps1` 做交叉验证时报

```
Run 1 chat intent mismatch. Expected 'analyze_wrong', got 'get_suggestion'.
```

**根因分两层**：

1. **客户端侧（真正的原因）**：Windows PowerShell 5.1 的 `Invoke-RestMethod` 在 body 为字符串时
   按 ASCII 编码，中文被替换成 `?`。实测服务端收到的原始字节里是
   `226d657373616765223a2020223f3f3f3f3f3f22`（即 `"message": "??????"`）——
   **中文在发出之前就已经丢了**，服务端无能为力。
2. **服务端侧（可加固点）**：`app/api/chat.py` 原来只用 `request.get_json(silent=True)`，
   而 Flask 在 `Content-Type: application/json; charset=utf-8` 下会因不识别 charset 参数而返回 `None`，
   导致消息为空 → 意图识别**静默退化**为 `get_suggestion`。这会把"客户端编码问题"变成"接口答非所问"，
   极难排查。

**修复**：
1. `app/api/chat.py` 新增 `_payload()`：`get_json` 失败时**取原始字节再按 UTF-8 显式解码**重试。
   注意不能用 `get_data(as_text=True)`——它会按猜测的字符集解码，在带 `charset=utf-8` 时可能解成乱码。
2. `tools/run_backend_core_regression.ps1` 的 chat 请求改为显式 UTF-8 字节 body +
   `Content-Type: application/json; charset=utf-8`。
3. 自检脚本新增断言「带 charset=utf-8 时中文意图不丢失」，防止回归。

**验证**：`run_backend_core_regression.ps1` 现在 **10/10 次迭代全部通过**
（覆盖 submissionId 工作流交接、幂等、proactive、chat、snapshot）。

> 💡 **这条对团队有实际价值**：以后任何人用 PowerShell / curl 手工试聊天接口，
> 都不会再看到"明明说的是错题，它却给我学习建议"这种莫名其妙的现象。

### 🟠 缺陷：工程自带的 PowerShell 脚本在 Windows PowerShell 5.1 下**完全无法运行**（已修复）

**发现过程**：为验证重构后旧回归脚本是否仍可用，直接执行 `tools/run_backend_core_regression.ps1`，
得到一堆语法错误：

```
The string is missing the terminator: '.
Unexpected token '}' in expression or statement.
The hash literal was incomplete.
```

**根因**：这些脚本含有中文（注释与断言消息），文件保存为 **UTF-8 无 BOM**。
Windows PowerShell 5.1 在没有 BOM 时**按系统 ANSI 代码页（简体中文为 GBK）解析脚本**，
一个中文字符被读成两个字节，很容易吃掉引号或大括号，于是**整个脚本语法崩溃**。

**影响面**：`tools/` 下 5 个脚本受影响（`run_backend_core_regression.ps1`、`run_fixture_ui_flow.ps1`、
`run_focus_ui_flow.ps1`、`run_local_feature_ui_flow.ps1`、`run_ui_navigation_smoke.ps1`）——
**也就是说，这些回归脚本在团队的 Windows 环境下很可能从来没有真正跑通过。**

**修复**：为所有含非 ASCII 字符的 `.ps1` 补上 **UTF-8 BOM**（`EF BB BF`）。
另 3 个纯 ASCII 脚本无需改动。现在 9 个脚本**全部通过 PowerShell 语法解析**。

> 💡 **给团队的经验**：本项目所有 `.ps1` 必须保存为 **UTF-8 with BOM**（`.py` 用 UTF-8 即可）。
> 新建脚本后建议先跑一次
> `[System.Management.Automation.Language.Parser]::ParseFile(...)` 自检。
> `tools/start_dev.ps1` 已按此规则保存。

### 8.1 问题一：工程用了 ArkUI-X 插件，hvigor 直接失败

**现象**：在 DevEco 中 Sync 报错

```
hvigor ERROR: 00303207 Configuration Error
Unable to find 'arkui-x.dir' in 'local.properties' or 'ARKUIX_SDK_HOME'
```

**根因**：工程是从 **ArkUI-X 跨平台模板**初始化的：

| 文件 | 原内容 |
|---|---|
| `hvigor/hvigor-config.json5` | `"@ohos/hvigor-ohos-arkui-x-plugin": "4.26.1"` |
| `hvigorfile.ts` | `export { AppTasksForArkUIX } from '@ohos/hvigor-ohos-arkui-x-plugin'` |
| `entry/hvigorfile.ts` | `export { HapTasks } from '@ohos/hvigor-ohos-arkui-x-plugin'` |

ArkUI-X 插件启动时**强制**要求 ArkUI-X SDK 路径，本机未安装 → Sync 失败。

**为什么不装 ArkUI-X SDK 而是改插件**：工程 `build-profile.json5` 的 `runtimeOS` 已是
`HarmonyOS`，仓库里**没有** `.arkui-x/` 目录，参赛只需要 HAP 包 —— ArkUI-X 对本项目零收益，
却多出一个必须配置的 SDK 依赖（现场演示多一类翻车风险）。故切回标准插件。

**修复**（3 个文件）：`dependencies` 清空为 `{}`；两个 `hvigorfile.ts` 改为：

```typescript
import { appTasks } from '@ohos/hvigor-ohos-plugin';   // 根目录
export default { system: appTasks, plugins: [] }

import { hapTasks } from '@ohos/hvigor-ohos-plugin';   // entry 模块
export default { system: hapTasks, plugins: [] }
```

> ⚠️ **踩坑记录**：中途曾把 `"@ohos/hvigor-ohos-plugin": "6.24.3"` 写进 `dependencies`，
> 结果 hvigor 让 pnpm 去 `registry.npmjs.org` 拉包 → `ERR_PNPM_FETCH_404`。
> **该插件不在 npm 仓库**，必须留空依赖，由 DevEco 的本地插件目录自动链接
> （日志里的 `is linked to ... from D:\DevEco\...\hvigor-ohos-plugin` 即该机制）。

## 9. 追加修复：登录后无法返回登录页（2026-09-18）

### 9.1 问题

登录页进入 App 后，**没有任何路径可以回到登录页**：

* `EntryAbility.restoreIdentity()` 只在**冷启动**时判断要不要进登录页；
* 「我的」页只有「退出登录」与「注销账号」，两者都**留在 App 内**回到体验身份；
* 一旦进了 App，想换身份只能杀进程重装或清数据。

这是典型的"**能进不能出**"设计缺陷 —— 对参赛作品来说规范性上会被扣分，
演示时也容易把自己困住（比如演示完注册账号后想切回演示身份）。

### 9.2 修复

在 `pages/Account.ets` 新增**常驻**的「返回登录页」按钮（无论登录态 / 体验身份都可见），
位于身份说明卡与「退出登录」之间，点击走二次确认浮层。

核心逻辑 `goToLogin()`：

```typescript
private async goToLogin(): Promise<void> {
  this.showSwitchConfirm = false;
  this.busy = true;
  if (AuthStore.isSignedIn()) {
    await AuthClient.signOut();      // 已登录时必须先真正退出
    appState.applyLogout();
    this.clearLocalCaches();
  }
  this.busy = false;
  router.replaceUrl({ url: 'pages/Login' });   // replace 而非 push
}
```

**两个关键决定**：

1. **已登录时必须先 `signOut()`**，不能只跳页。否则 `AuthStore` 里登录态还在，
   下次启动 `EntryAbility` 又会直接进主页 —— 用户会觉得"我返回登录页了，
   怎么一重启又进去了"。
2. **用 `replaceUrl` 而不是 `pushUrl`**。登录页是身份入口，不该在返回栈里累积；
   否则在登录页按返回又回到「我的」，逻辑上很怪。

顺带把体验身份下的「建立我的账号」也改走同一条确认路径，两处行为统一。

### 9.3 现在三个出口的分工

| 出口 | 去哪 | 凭据与数据 |
|---|---|---|
| **返回登录页** | 登录页，可换**任意**身份 | 已登录则退出并吊销 token |
| **退出登录** | 留在 App 内 → 体验身份 | 吊销 token；账号数据留在服务端 |
| **注销账号** | 留在 App 内 → 体验身份 | 账号停用 + 全部会话失效，**不可撤销** |

Account.ets：0 ERROR，3 条废弃警告（replaceUrl / back，工程既有同类警告 70+ 条）

### 10.2 标签栏高亮不跟随的 bug（用户报告）

**现象**：切换标签后页面内容变了，但底部高亮一直停在「首页」。

**根因**：ArkTS 的 @Builder **函数参数按值传递**，参数变化不会触发该 Builder
重新求值。原写法

``typescript
this.BottomNavItem('⌂', '首页', this.activeTab === 0, () => this.activeTab = 0)
``

里的 ctive 是**初次渲染时算好的布尔值**，切换后不会重算 —— 所以永远停在首页。

**修复**：标签栏改为**无参 @Builder**，高亮在 Builder 内部**直接读 	his.activeTab**
（@State 变化会驱动该范围重建）：

``typescript
@Builder
TabBar() {
  Row({ space: 4 }) {
    this.TabItem('⌂', '首页', 0)
    this.TabItem('◷', '计划', 1)
    this.TabItem('◵', '记录', 2)
    this.TabItem('◉', '我的', 3)
  }
  ...
}

@Builder
TabItem(icon: string, label: string, index: number) {
  // 只接收静态参数，高亮一律由 this.activeTab 推导
  Column() { ... }
  .backgroundColor(this.activeTab === index ? '#EFF6FF' : '#FFFFFF')
  .onClick(() => { this.activeTab = index; })
}
``

旧的 BottomNavItem（带 ctive/ction 参数的版本）已删除，
避免后人再照抄这种会导致同一 bug 的写法。

> 💡 **经验**：ArkTS 里**不要把状态当参数传给 @Builder**。
> 需要响应状态变化的 Builder 应当无参，在内部读 	his.xxx。
> 参数只用于**静态**内容（文案、图标、下标）。
