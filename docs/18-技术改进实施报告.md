## 一、后端改进（全部已验证）

### 1.1 ✅ `405` / `414` / `415` / `413` 统一返回 JSON

**原先**：Flask 默认只把 404/400/500 交给我们注册的处理器；
**方法不允许**（405）与 **URI 过长**（414）返回的是 **HTML 错误页**。
前端 `ApiResponseValidator` 按 JSON 解析，拿到 HTML 会直接报
`INVALID_RESPONSE`，表现为"后端崩了"，实际只是用错了方法。

**现在**：`app/__init__.py` 为 405/413/414/415 各注册了 JSON 处理器，
统一返回 `{errorCode: "BAD_REQUEST", message, details}`。

**验证**：

```bash
$ pytest -q tests/test_technical_improvements.py
# test_method_not_allowed_returns_json[get-/api/v1/workflows-405]
# test_method_not_allowed_returns_json[post-/api/v1/profile/demo-user-405]
# test_non_json_body_returns_json_400_not_html
# test_error_handlers_for_server_level_statuses_are_registered
```

联调实测：

```
[PASS] 方法不允许 → 405 且返回 JSON errorCode  | HTTP 405 body=dict
[PASS] 非 JSON 请求体 → JSON 400（不是 HTML 错误页）  | HTTP 400 body=dict
```

**一个诚实的说明**：`test_client` **不会触发 414** —— 414 是 WSGI/HTTP
服务器层判定的（请求行长度上限），Flask 测试客户端不施加该限制。
所以 414 的处理器用"直接调用处理器"的方式测，**真实触发未在联调里覆盖**。
这不算大问题（前端几乎不会发超长 URL），但**如实记在这里**。

### 1.2 ✅ CORS 收敛（不再反射任意 Origin）

**原先**：裸 `CORS(app)` → 反射任意 `Origin`，任何网站都能带着用户凭据调本服务。

**现在**：白名单正则，只放行本机开发与私有网段；可用
`ZHIXUE_CORS_ORIGINS` 覆盖（填 `*` 可临时恢复，仅供排障）。

**为什么不能收太死**：HarmonyOS 真机通过局域网 IP 访问，桌面预览用
`localhost`，把这两类挡住会让联调直接失效。

**验证**：

```
[PASS] CORS 不反射任意 Origin（原先裸 CORS(app)）  | Access-Control-Allow-Origin=None
[PASS] CORS 仍放行本机开发来源（收紧不能误伤联调）  | Access-Control-Allow-Origin='http://localhost:8080'
```

`test_cors_allows_private_lan_origin_for_real_device` 还专门覆盖了
`http://192.168.1.20:5000`（真机场景）。

### 1.3 ✅ 对话历史按用户隔离

**原先**：`chat/history.json` 是**一个全局 JSON 数组**，所有用户混在一起。
`GET /api/agent/history` 返回**所有人的聊天记录**，`DELETE` 会**清空所有人**。
聊天记录属个人信息，这是真实的越权（审计已报）。

**现在**：按 `userId` 分桶存储：

```json
{ "demo-user": [...], "u-xxxx": [...] }
```

- 身份用项目统一的 `resolve_user_id()`：**已登录 > 显式 `userId` > 演示身份**
- 响应回传 `userId`，便于前端确认读到的是谁的历史
- **兼容旧格式**：读取时把旧的扁平数组一次性归给 `demo-user`，老数据不丢

**验证**：

```
[PASS] 对话历史按用户隔离（甲只看得到自己的）  | 甲的历史=['甲的问题']
[PASS] 清理甲的历史不影响乙（原先 DELETE 会清空所有人）  | 乙的历史=['乙的问题']
```

另有 6 项 pytest 覆盖（含旧格式迁移、分桶落盘结构）。

### 1.4 ✅ SQLite 可选后端（架构层最大的一笔债）

**问题**：`JsonRepository` 每次 `save()` **全量重写整个 JSON 文件**。
实测代价随数据量线性增长：

| 已存记录 | JSON 单次 save | SQLite 单次 save |
|---|---|---|
| 50 条 | **5.60 ms** | 0.04 ms |
| 200 条 | **14.02 ms** | 0.03 ms |
| 800 条 | **52.37 ms** | 0.03 ms |

`save×200` 总量：**JSON 1640.9 ms vs SQLite 13.1 ms（约 125 倍）**。

**关键发现**：仓库里**本来就有 `sqlite_repository.py`**，只是主链没用它。
而且它**缺一个 `clear()` 方法** —— 一旦切过去，`demo/reset` 与鉴权会话清理
会直接 `AttributeError`。已补齐。

**现在**：`ZHIXUE_DB` 选择后端，默认仍是 `json`（JSON 文件可直接肉眼查看、
便于答辩演示与人工核对）：

```powershell
$env:ZHIXUE_DB="sqlite"; python run.py            # 用 <数据目录>/repository.sqlite
$env:ZHIXUE_DB="sqlite:E:\temp\data.sqlite"       # 指定路径
```

**踩过并修掉的坑（值得记录）**：第一版**每个方法都新开连接**，并在
`_connect()` 里执行 `PRAGMA journal_mode=WAL`。结果是每次读写都要切换
journal 模式并 fsync —— 基准测试 1280 次 save **超过 120 秒**都没跑完，
比 JSON 版慢几个数量级，完全违背"换 SQLite 是为了快"的初衷。
现改为**单长连接 + 一次性 PRAGMA + 可重入锁**。

**验证**：

- `tests/test_sqlite_backend.py`：**15 个测试函数 / 24 个用例**，其中
  `repository` fixture 参数化，**同一套 `Repository` 契约断言同时跑两个后端**
- `test_demo_baseline_identical_across_backends[json|sqlite]`：
  在**子进程**里起真实服务器，验证两个后端下演示基线数字一致
  （66.67 / 42→58 / 版本 1→2）
- `test_sqlite_repository_connection_is_reused`：用墙钟时间约束，防止退回"每调用一连接"
- 一键联调**在两个后端下各跑一次**，均 `95/95 PASS`

**迁移工具**：`tools/migrate_repository.py`（`--dry-run` / `--verify` / `--to-json`），
**只读源文件**，随时可切回。

### 1.5 ✅ 知识库语义检索（embedding + 关键词混合）

**原先**：纯关键词 + 标签（`0.5*tag + 0.3*keyword + 0.2*heading`）。
短板是同义表达完全命中不到 —— 资料里写"二叉树的后序遍历"，
问"如何按左右根的顺序访问节点"就搜不到。

**现在**：新增 `app/agent/semantic.py`，用 DashScope `text-embedding` 编码后
按余弦相似度**加权融合**：

```
final = 0.4 * keyword_score + 0.6 * normalized_cosine
```

**四条设计原则**（与项目其它地方一致）：

1. **诚实降级**：无 Key / 调用失败 → 退回纯关键词，并在 `retrievalMode`
   里如实标注 `keyword+tag`；成功时是 `hybrid:semantic+keyword+tag`
2. **不静默改变既有行为**：拿不到向量时分数与第一期**逐位相同**
   （`blend(x, None) == round(x, 4)`）
3. **可测试**：`encode` 可注入，无网络也能用确定性假向量验证融合逻辑
4. **有界 + 不丢数据**：只对关键词分前 `MAX_EMBED_CHUNKS` 个切片编码，
   超出部分保留关键词分而**不丢弃**

**契约同步**：`KnowledgeSearchResponse` 补入
`retrievalMode` 的 hybrid 枚举值 + `semanticAvailable` + `semanticWeight`
（`tools/patch_contract_semantic.py`）。

**顺带发现**：前端 `KnowledgeBase.ets:596` **已经会显示**
`检索方式：${retrievalMode}` —— 也就是说只要后端如实标注，
界面上就能直接看到当前是不是真的在跑语义检索。

**验证**：`tests/test_semantic_search.py` **23 项**（纯函数 / 融合 / 降级 / API 标注），
联调新增：

```
[PASS] 知识库检索可用  | HTTP 200 hits=1
[PASS] 检索方式被诚实标注（keyword+tag 或 hybrid）
[PASS] 语义能力与权重自洽（不伪装）  | semanticAvailable=False semanticWeight=0.0
```

### 1.7 ✅ 一个我曾误判并已回退的项（如实记录）

审计清单里有一条 **"`maxSteps=1` 时 `for/else` 会把正常结束误标 `status=error`"**。

我按这个判断改了 `app/runtime/loop.py`，写了回归测试 —— 然后发现：

1. **该缺陷不存在**。`for ... else` 的 `else` 在"循环未被 `break`"时执行；
   而 `finish` / `waiting` / `error` 三条出口都自带 `break`，
   所以 `max_steps` 恰好用满时**不会**误标。
2. **`else` 是可达到的**，而且在那种情形下报错是**正确的**：
   跑满 `max_steps` 仍未进入终态，就是真的超限。
3. **我的"修复"反而真的弄坏了 `waiting` 场景** ——
   `waiting` 分支把 status 写成 `"running"`，我改用"循环后按 status 判定"
   之后，正常等答题被误判成 `max_steps` error（对照实验：改写版 1 例误判 / 原版 0 例）。

**已完全回退**，`run_workflow` 的**字节码与改动前逐指令一致**
（`co_code` 相同、325 条指令序列相同，只有 docstring 文本不同）。
并在 docstring 里写明了这次误判的经过，另补了 6 项测试把**真实边界行为**固化。

> **教训**：`for/else` 读起来像 bug，但它在这里恰好表达了想要的语义。
> 改这类"看起来可疑"的控制流之前，必须先用受控实验把行为测出来。

### 2.2 ✅ token 加密存储（AES-256-GCM + 资产库托管密钥）

**原先**：`AuthStore.ets` 把 token **明文**写进 preferences：

```typescript
store.putSync(AuthStore.KEY_TOKEN, session.token);   // 明文
```

preferences 在应用私有目录，未 root 的机器上外部读不到，但它**不是安全存储**：
备份、调试桥、任何拿到沙箱的途径都能读出明文 token，而 token 等同账号
（有效期 30 天）。

**现在**：新增 `api/TokenCipher.ets`

- **数据密钥**用系统**资产库**（Asset Store Kit）托管
- **token 密文**用 AES-256-GCM 加密后存 preferences，**每条消息独立 nonce**，
  GCM 自带完整性校验（被篡改会解密失败而不是静默返回垃圾）
- **兼容旧数据**：`looksEncrypted()` 识别不了密文格式就按"升级前的明文"处理，
  老用户不会因为这次改动被动掉线
- **兜底可用**：加密不可用时**降级为明文**并把 `AuthStore.encryptionDegraded()`
  置为 true，由账号页如实提示 —— **不会把登录打挂**，也不静默假装安全

**符号核验**（本机 SDK，逐个确认存在）：
`cryptoFramework.createSymKeyGenerator` / `createCipher` / `createRandom`、
`generateSymKey()`、`convertKey(key: DataBlob)`、`getEncoded()`、`CryptoMode`、
`GcmParamsSpec`（`iv`/`aad`/`authTag`）、`generateRandomSync(len)`、
`initSync`、`doFinalSync`、`asset.Tag.{ALIAS,SECRET,RETURN_TYPE,ACCESSIBILITY}`、
`asset.ReturnType.ALL`、`asset.Accessibility.DEVICE_FIRST_UNLOCKED`、
`asset.query|add|remove`、`util.Base64Helper.encodeToStringSync|decodeSync`。

#### 专项核验抓出的一个 P0 bug（已修）

我请了一次专项核对（报告：`docs/20-token加密API核验报告.md`，
含全部 d.ts 行号与官方文档原文引证），**抓出我第一版的致命错误**：

```typescript
// ❌ 我第一版写的
const merged: Uint8Array = TokenCipher.concat(cipherText, authTag);
cipher.doFinalSync({ data: merged });
```

GCM 的 tag 是对 `AAD ‖ ciphertext` 计算的。解密时算法库会拿**喂进去的全部字节**
当密文重算 tag，于是既与 `spec.authTag` 不匹配，那多出的 16 字节还会被当密文
多解一段垃圾 → `doFinalSync` 抛 `17630001` → 被 catch 吞掉 →
**`decrypt()` 永远返回 `null`**，表现为"**所有已登录用户每次冷启动都被当成未登录**"。

```typescript
// ✅ 正确：只传纯密文，tag 只走 GcmParamsSpec.authTag（在 initSync 时给出）
cipher.doFinalSync({ data: cipherText });
```

官方 FAQ 明确把 **key / iv / aad / tag / ciphertext 列为 5 个独立输入**。

同一次核验还确认了这些（都已在代码里）：

| 结论 | 依据 |
|---|---|
| `initSync(opMode, key, params)` 是 **3 参数**，`params` 可为 null | d.ts `:3551`（我原先抓到的 `initSync(priKey)` 是 `Sign` 接口的，不是 `Cipher`） |
| `createSymKeyGenerator('AES256')` —— **不带** `\|GCM` | 密钥生成规格里 AES 只有"算法+长度"两段 |
| `doFinalSync` 输出**末尾 16 字节确实是 tag** | 官方 GcmParamsSpec 表原文（4 个修订版逐字一致） |
| **不存在** `CipherSpecItem.AEAD_TAG_LEN` | `CipherSpecItem` 仅 5 项，全是 RSA/SM2 相关 |
| `convertKeySync({data})` 是导入裸密钥的正确方式 | d.ts `:2006`；AES256 必须正好 32 字节 |
| `CONFLICT_RESOLUTION = OVERWRITE` 单次 add 才幂等原子 | d.ts `:927`；默认 `THROW_ERROR`(`:941`)。原先 `remove`+`add` **非原子**，两步之间崩溃会**永久丢失密钥** |

#### 一处仍未实测

**「`doFinalSync(明文)` 一次调用（不走 `update`）在所有情况下都返回 `密文‖tag`」**
—— 官方示例只演示了 `update + doFinal(null)`；"末尾 16 字节是 tag"来自
API 参考表格约定。本机无设备可实测。

若要 100% 对齐官方示例，加密侧可改为
`updateSync(明文)` + `doFinalSync(null)`（此时结果恰好 16 字节 tag，无需切片）。

**兜底已就位**：`AuthStore.encodeToken()` 在加密失败时会**降级为明文**并把
`encryptionDegraded()` 置为 `true`，由账号页如实提示。
**即使上述约定有偏差，应用仍能正常登录**，只是退回改动前的存储强度。

**仍然存在的边界（不夸大）**：密钥是**软件密钥**，不是 HUKS 硬件密钥。
HUKS 的密钥不出安全区、安全性最高，但其 `initSession`/`finishSession`
需要多轮异步交互，与 `AuthStore` 的**同步** preferences 范式不兼容。
混用会引入"写了一半"的状态，因此选择"软件密钥 + 系统资产库托管"。

### 2.4 ✅ 响应式布局（能力已就位，逐页落地留给前端）

但**全工程零断点代码** —— 所有页面按手机竖屏写死，在平板/PC 上会被拉伸。

**现在**：新增 `utils/DeviceLayout.ets`

- 在 `EntryAbility.onWindowStageCreate` 绑定主窗口，监听 `windowSizeChange`
- 三档断点：`phone`（<600vp）/ `tablet`（600–839vp）/ `desktop`（≥840vp）
- `contentMaxWidth()`：大屏返回 720vp 限制正文宽度，手机返回一个足够大的
  有限值（**不能返回 `Infinity`** —— 它不是合法的 `Length`）
- `classify()` 是纯函数，便于单测

**已应用到**：`Login.ets`（首屏最关键）—— 大屏限宽居中、
顶部留白从 56vp 收到 32vp。

**未应用**：其余 18 个页面。**这是刻意的取舍**：完整响应式改造会牵动全部
页面，在**无法编译验证**的环境里风险过高。因此本轮只提供"判断 + 限宽"
这一层能力并示范一个页面，逐页落地列在 `19-未完成事项清单.md`。

**新增前端单测**：`entry/src/test/DeviceLayout.test.ets`（8 个用例，已注册进
`List.test.ets`），覆盖三档边界值与"手机端 maxWidth 必须有限"。

### 2.5 未做：`@ohos.router` → `Navigation` 迁移

**61 处**废弃的 `@ohos.router` 调用**没有迁移**。理由：

- `@ohos.router` 在 API 24 上**仍然可用**（只是标记废弃），不构成功能问题
- 迁移涉及 19 个页面的路由声明、参数传递、返回栈，是**结构性改动**
- 在无法编译验证的环境里做这种改动，**风险远大于收益**

已列入 `19-未完成事项清单.md`，并给出分批迁移建议。
