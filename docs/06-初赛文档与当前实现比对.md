## 一、结论（先给答案）

> ### agent 逻辑**没有大改**；但**判断层的数学模型改了**，而且改得不少。

拆成三句可对外说的话：

1. **骨架没动**。五层 Agent 工作流（输入→理解→判断→行动→输出）、四因子搭子匹配 40/25/20/15、每一层输出可解释依据——这三根承重墙与初赛文档**逐字对应，一行没改**。
2. **判断层的算分模型换了**。初赛文档写的是**三因子整数评分**（考试紧迫度 + 复习状态 + DDL 紧迫度，0—100 分，≥80 高 / 40—79 中 / <40 低）；当前实现是**五因子加权连续分**（掌握度 .30 + 错误强度 .25 + 重要度 .20 + 紧迫度 .15 + 先修影响 .10）。**这不是调参，是换了一套模型**——因子从 3 个变 5 个，口径从整数变小数权重，证据结构从「总分」变成「逐因子 value / weight / contribution 三元组」。
3. **界面层改动幅度很大**，且是**定稿方向的变化**，不是实现偏差。初赛文档描述的是「首页 = 学习决策中枢，底部五层工作流进度，学习/专注双入口」的 **Hub-and-Spoke** 结构；当前实现是**对话优先 + 底部四标签**，首页（中枢）被降级为「智能体」标签页。

**一句话总结给评委**：产品理念与 Agent 架构一脉相承，复赛做的是把判断层从「拍脑袋的整数打分」升级为「可逐项验算的加权模型」，并把入口从「功能大厅」收敛为「直接对话」。

## 三、逐条核验：**变了**的部分

### 3.1 判断层算分模型：三因子整数 → 五因子加权（**实质性变更**）

**初赛文档 §3（3）判断层原文口径**：
> `judgeOptimalTask()` 综合**考试紧迫度（权重最高）、复习状态和 DDL 紧迫度三项因子**，为每门课程计算 **0-100 分**的优先级评分，**≥80 分为高优先级（建议 45 分钟），40-79 分为中优先级（建议 30 分钟）**……

配套的**表 5** 也是整数口径，例如「数据结构：+35（≤7天）+30（复习不足）+25（DDL≤2天）+15 → **105→100（上限）**」。

**当前实现**（`server/zhixue-agent-server/app/decision/priority.py`，文件首行即自述 *"Transparent five-factor learning priority engine."*）：

```python
# config.py
PRIORITY_WEIGHTS = {
    "mastery": 0.30,             # 掌握度越低越优先
    "errorIntensity": 0.25,      # 错误强度
    "importance": 0.20,          # 知识点重要度
    "urgency": 0.15,             # 考试紧迫度
    "prerequisiteImpact": 0.10,  # 先修影响
}
```

```python
# priority.py L47-64
factor_values = {
    "mastery":            round((100 - mastery) / 100, 4),
    "errorIntensity":     round(_number(item.get("errorIntensity", ...)) / 100, 4),
    "importance":         round(_number(item.get("importance", 50)) / 100, 4),
    "urgency":            round(_number(item.get("urgency", urgency)) / 100, 4),
    "prerequisiteImpact": round(_number(item.get("prerequisiteImpact", 0)) / 100, 4),
}
factors = {name: {"value": value,
                  "weight": PRIORITY_WEIGHTS[name],
                  "contribution": round(value * PRIORITY_WEIGHTS[name], 4)}
           for name, value in factor_values.items()}
score = round(sum(item["contribution"] for item in factors.values()), 4)
strongest = max(factor_values, key=factor_values.get)
reason = f"{strongest} 因子值为 {factor_values[strongest]:.2f}，应优先安排针对性练习"
```

**差异清单**：

| 维度 | 初赛文档 | 当前实现 | 说明 |
|---|---|---|---|
| 因子个数 | 3（紧迫度 / 复习状态 / DDL） | **5**（掌握度 / 错误强度 / 重要度 / 紧迫度 / 先修影响） | 复习状态与 DDL 紧迫度被**掌握度 + 错误强度 + 紧迫度**取代 |
| 计分口径 | 整数加分（+35 / +30 / +25），人工设 100 上限截断 | 归一化到 0—1 后**加权求和**（权重和 = 1.00），**天然落在 0—1** | 不再需要「105→100 上限」这种硬截断 |
| 可解释粒度 | 总分 + 分档标签 | **逐因子 `value` / `weight` / `contribution` 三元组** | 评委可以当场手算复现 |
| 排序理由 | 分级文案 | 自动取 `strongest` 因子生成一句归因（`reason`） | 归因由代码生成，不靠人写死 |
| 分档动作 | ≥80 高→45 分钟 / 40—79 中→30 分钟 / <40 低 | 时长改由**计划重规划规则**产出（演示基线 V1 `[30,30]` → V2 `[45,15]`） | 分档与排期解耦 |

**这不是「调参」，理由有三**：
- 因子集合变了（3 → 5），其中「先修影响」在初赛文档里**完全不存在**；
- 数学形式变了（整数加法 + 截断 → 归一化加权和），量纲从 0—100 变为 0—1；
- 证据结构变了（总分 → `factorDetails` 数组），前端因此需要专门的 `FactorBreakdownCard` 来渲染——**这个组件在初赛文档里没有**。

### 3.2 掌握度更新规则：新增了「答错要掉分」

初赛文档未描述掌握度的具体更新公式。当前实现（`app/tools/assessment_tools.py` L47—61）：

```python
def update_mastery(old_score, assessment_score):
    if assessment_score == 100:   delta = 29
    elif assessment_score >= 60:  delta = 16
    elif assessment_score >= 40:  delta = 4
    else:                         delta = -4
    return max(0, min(100, old_score + delta))
```

- **收益**：全对才大涨（+29），及格小涨（+16），不及格微涨（+4），**低于 40 分要扣分（−4）**。
- 演示基线可验证：初始掌握度 **42**，提交 3 题对 2 题 → 得分 **66.67** → 掌握度 **42 → 58**（+16，落在 ≥60 档）。
- **这修掉了初赛原型的一个硬伤**：原实现「无论答对答错掌握度都上涨」，无法解释「为什么练了还错」。

### 3.3 判分：从「与答案无关」改为「真判对错」

当前实现 `grade_exercise()`（`assessment_tools.py` L12—44）依据 `_ANSWER_KEYS` 逐题比对：

```python
correct_ids = [i for i in valid_ids if submitted[i] == answer_keys[i]]
score = round(len(correct_ids) / max(1, len(valid_ids)) * 100, 2)
```

- 并以 `knowledgePointId` 聚合出 `per_knowledge_accuracy`。
- 演示三题锁定值：`exercise-preorder-001="A"`、`exercise-inorder-001="B"`、`exercise-postorder-001="C"`，同属知识点 `binary-tree-postorder`；提交 `√√×`（A/B/A）→ **66.67**。
- 回归自检中「新账号判分同样为 66.67」「新账号掌握度 0→16」两项专门守这条规则**对真实注册账号也生效**。

### 3.4 重规划：从「不幂等、会漂移」改为「幂等可复现」

当前实现的计划重规划带 `idempotencyKey`（`api/exercises.py` L109—116），同一 key 重复提交得到同一结果；回归里有一条断言就叫「第二次 /run 后 status = completed」，确保**演示可重复播放**。

### 3.6 LLM 与确定性代码的边界（复赛新增的核心架构主张）

- 这一设计的用意：**演示可用性优先于安全洁癖**——评审过程中一个过期 token 不该让整个 App 不可用。

## 六、答辩口径（可直接背）

**被问「你们复赛和初赛比，Agent 逻辑大改了吗？」**

> 「架构没改，判断层升级了。五层工作流、四因子搭子匹配 40/25/20/15、每层可解释依据，这三样从初赛到现在一行没动。
> 改的是判断层的算分模型：初赛是三因子整数打分，会出现『105 分截断到 100』这种要靠人工设上限的情况；复赛换成五因子归一化加权——掌握度、错误强度、重要度、紧迫度、先修影响，权重和正好是 1，天然落在 0 到 1。每个因子都返回 value、weight、contribution 三元组，**评委可以当场手算复现**。
> 同时我们修了三个真 bug：判分原来跟答案无关、掌握度答错也涨、重规划不幂等会漂移。现在这三个都有回归断言守着。
> 界面确实重构了：初赛是功能大厅，复赛改成进来就能直接说话——**能力一个没少，只是不再逼用户先读一遍功能清单**。」

**被问「你们的大模型用在哪？」**

> 「大模型只负责回答『**下一步该叫谁**』，加上自然语言回复和 Qwen-VL 识图。判分、掌握度、优先级、重规划**全部是确定性代码**——模型挂了系统照样闭环。这一点我们写成了自检断言：无 LLM 时两次运行的 agent 序列必须完全一致。」
