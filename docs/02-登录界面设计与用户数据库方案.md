## 0. 三句话结论

### ① 登录界面要"轻"，而且是"Agent 的身份锚点"，不是"门禁"

本项目**不需要**一个拦在门口的账号密码墙。它需要的是一个 **30 秒内能进、且让 Agent 记住你是谁**的轻登录页。原因是评分结构决定的：

| 评分项 | 分值 | 登录界面能贡献什么 |
|---|---|---|
| 创新性 | **50** | 几乎为 0（登录不是创新点） |
| 完备度 | 20 | **+1～2**（"多用户/跨设备"的完备性叙事） |
| 前景评估 | 20 | **+1～2**（"可落地"的必要工程环节） |
| 规范性 | 10 | 中性 |
| 应用价值 | 20 | 中性（HAP 与上架才是重点） |

> **结论**：登录界面是**必要但不紧急**的工程件。**绝不能让它挤占服务卡片 / 代理提醒的档期。**

### ② 适配度**很高**，但有一个必须先修的前置障碍

工程里**已经有**：`UserProfile` 模型、`AppState.currentUser` 单例、后端所有接口都带 `userId` 参数、`preferences` 持久化能力、完整的设计规范（主色 `#2563EB`、12–20vp 圆角、每页一个实心主按钮）。

**唯一的前置障碍**：**用户身份现在是分裂的**——前端 `u001`、后端 `demo-user`（详见 [`01-下一步改进分析与建议.md`](01-下一步改进分析与建议.md) §2.1）。**不先统一它，登录功能做在哪一边都是错的。**

### ③ 用户数据库：**推荐用华为 AppGallery Connect（AGC）云数据库 + 认证服务**

鸿蒙原生支持、零运维、有免费额度、评委认可度高，且能顺带拿到"鸿蒙特性"数量。**这是本次参赛的最优解。**
自建后端数据库是可行的备选，但对一个 12 天内要冻结的项目来说，**运维风险 > 技术收益**。

> ⚠️ **12 天窗口下的诚实建议**：如果 [`01`](01-下一步改进分析与建议.md) §3 的 P0 三项（服务卡片 / 代理提醒 / 配 Key）还没做完，
> **登录功能应该做成"最小可用版"（昵称 + 演示账号快速进入 + 本地持久化），数据库用 AGC 或干脆先本地**，
> 把剩下的时间全部留给 50 分的创新性。

## 1. 为什么这个产品需要登录（先讲清楚"为什么"，再讲"怎么做"）

### 1.1 三条真实的业务理由（答辩时要能脱口而出）

| # | 理由 | 具体场景 |
|---|---|---|
| **1** | **"学习搭子匹配"本质上需要多用户身份** | 现在 `mock_candidates.json` 里固定 3 个假候选人（小红/小刚/小丽）。评委一问"两个真人怎么匹配上"就答不上来。有了登录，**两台设备两个账号，就能演示真实的互相邀请** |
| **2** | **"主动服务"要求记住用户** | 服务卡片显示"你上次后序遍历只答对 2/3"——**必须知道"你"是谁**，否则换台设备就失忆，`/api/v1/agent/proactive` 的 `lastStudyAt`、`masteryScore` 全部失真 |
| **3** | **"成长陪伴"需要连续的时间线** | 掌握度从 42 → 58 → 71、连续学习 7 天、徽章体系——这些**跨会话的状态必须有归属主体** |

### 1.2 反过来：登录界面**不该承担**的职责

- ❌ 不该做"不登录就不能用"的硬门禁（演示时评委点不进去 = 灾难）
- ❌ 不该做复杂的企业级账号体系（手机号 + 验证码 + 密码 + 找回 + 实名……）
- ❌ 不该让登录页成为 App 的第一屏（本项目的第一屏应该是**首页的 Agent 感知状态**）

> **正确姿势**：**游客优先 + 一键进入 + 可选的登录升级**。
> 未登录也能跑通全部 16 个页面（用约定的 `demo-user`），登录只是把 `userId` 从"演示身份"换成"真实身份"。

## 2. 与整个项目的适配度分析

### 2.1 已有的适配基础（**好消息：适配度很高**）

| 已经存在的东西 | 位置 | 对新登录功能的意义 |
|---|---|---|
| `UserProfile` 完整模型 | `models/AgentModels.ets` | 用户信息结构已定义，**登录后直接填充即可** |
| `appState.currentUser` 全局单例 | `data/AppState.ets` | **已有"当前用户"的单一读点**，登录只需写它 |
| 所有后端接口都带 `userId` | `/api/v1/profile/{userId}`、`proactive.userId`、`submit.userId` | **后端已经支持多用户参数**，不用改契约 |
| `preferences` 持久化能力 | `ApiEnvironmentStore.ets`、`FixtureDemoStateStore.ets` | 登录态的本地存储**有现成范式可抄** |
| `AppState` 已有 `courses` / `homeworkDDLs` / `isDataImported` | `data/AppState.ets` | 登录后可把这些数据**绑到用户身上** |
| 完整设计规范 | `docs/前端README.md` §设计规范 | 登录页**直接用现成的视觉语言**，零设计成本 |
| 16 个页面已全部接入 AIFloatButton | `components/AIFloatButton.ets` | 登录页**也可以挂浮标**（"登录遇到问题？问问我"） |

### 2.2 必须先解决的前置障碍

#### 🔴 障碍 1：用户身份分裂（**做登录前必须先修**）

| 位置 | 当前值 |
|---|---|
| 前端 `MockData.ets` 的 `mockCurrentUser.userId` | **`u001`** |
| 前端 `ExerciseViewModel.ets` 兜底 | **`demo-user`** |
| 后端所有演示数据 | **`demo-user`** |

**做登录功能的第一个 commit 必须是统一这个 ID**，否则你会把分裂复制到登录逻辑里。

**建议改法**：在 `ApiDefaults.ets` 里加：

```typescript
/** 演示身份的默认用户 ID。后端演示数据全部挂在 demo-user 上，必须一致。 */
static readonly DEMO_USER_ID: string = 'demo-user';
```

然后 `MockData.mockCurrentUser.userId` 与所有 `?? 'demo-user'` 都引用它。

#### 🟠 障碍 2：后端目前**没有鉴权概念**

后端 100% 的接口都是"**谁传 userId 就信谁的**"——没有任何 token / session / 签名校验。这意味着：

- 现在的 `userId` 是**声明式**的，不是**认证式**的；
- 任何人把 `userId` 改成别人的，就能读到别人的画像（**IDOR 漏洞**，即"不安全的直接对象引用"）。

**参赛时的处理**：**在文档里主动写出来，并给出迁移路径**。这比被评委问出来强得多：

> "当前 `/api/v1` 处于**状态化演示实现**，`userId` 由客户端声明，尚未接入鉴权中间件。
> 生产化路径为：接入 AGC 认证服务获取 `accessToken` → 服务端校验 token 并从中解析 `userId` →
> 客户端不再自行声明身份。这一层已在契约中预留（`Authorization` 头）。"

#### 🟠 障碍 3：`JsonRepository` 是单文件存储，不适合多用户

`app/repositories/json_repository.py` 把全部数据写进一个 `data/repository.json`。演示足够，但**多用户真实使用会互相覆盖**。

好在这个仓库**已经做了接口抽象**（`repositories/repository.py` 定义了 `Repository` 协议，另有 `sqlite_repository.py`）——**换成 SQLite 只需要改 `create_app()` 里的一行**。这属于"架构已经准备好，只差接线"。

### 2.3 适配度总评

| 维度 | 适配度 | 说明 |
|---|---|---|
| **数据模型** | ⭐⭐⭐⭐⭐ | `UserProfile` 已定义，`AppState` 已有 `currentUser` 单点 |
| **后端契约** | ⭐⭐⭐⭐☆ | 所有接口已带 `userId`；**缺鉴权** |
| **存储层** | ⭐⭐⭐☆☆ | 已抽象 `Repository`，但默认实现是单文件 JSON |
| **UI 语言** | ⭐⭐⭐⭐⭐ | 设计规范现成，登录页零设计成本 |
| **导航结构** | ⭐⭐⭐⭐☆ | 16 页面已注册在 `main_pages.json`，加一页即可 |
| **与现有叙事的一致性** | ⭐⭐⭐⭐☆ | "搭子匹配"与"主动服务"都**需要**身份，登录是叙事补完而非外挂 |
| **对 50 分创新性的贡献** | ⭐⭐☆☆☆ | **几乎为 0——这是最重要的判断** |

> **一句话**：**技术上很好接，分值上很不划算。所以"做得对"比"做得多"重要得多。**

## 3. 登录界面怎么做（具体方案）

### 3.1 定位：三入口并行，游客优先

```
┌─────────────────────────────────────┐
│                                     │
│        知学 Mate                    │   ← Logo + 一句话价值主张
│   会主动找你的 AI 学习搭子            │      「会主动找你的 AI 学习搭子」
│                                     │
│  ┌───────────────────────────────┐  │
│  │   一键体验（推荐）             │  │   ← 主按钮（实心 #2563EB）
│  └───────────────────────────────┘  │      直接以 demo-user 进入首页
│                                     │      ★ 评委/演示永远点这个
│  ┌───────────────────────────────┐  │
│  │   手机号登录                   │  │   ← 描边按钮
│  └───────────────────────────────┘  │
│                                     │
│        使用昵称开始 →               │   ← 文字按钮（第三入口）
│                                     │
│  ─────────────────────────────      │
│  □ 我已阅读并同意《用户协议》《隐私政策》│   ← 必须勾选才能用手机号登录
└─────────────────────────────────────┘
```

**设计理由**：
- **"一键体验"是主按钮**：因为演示和评委验收是最高优先级，任何摩擦都是风险。
- **"昵称开始"是第三入口**：成本最低的"真实身份"——不涉及手机号，不涉及合规，但 `userId` 变成用户自己的了。
- 三个入口都不需要密码。**本项目没有任何需要密码保护的东西**（没有支付、没有隐私数据、没有账号资产）。

### 3.2 逐页设计

#### 页面 1：`pages/Login.ets`（新增）

| 区块 | 内容 | 说明 |
|---|---|---|
| 上部 40% | Logo + 主标题 + 一句话副标题 | 视觉留白，传递"轻"的感觉 |
| 中部 | 三个入口按钮 | 主按钮 1 个（一键体验），描边 1 个（手机号），文字 1 个（昵称） |
| 下部 | 协议勾选 + 隐私说明 | **必须的合规件**，文案要短 |
| 底部 | "跳过，先看看 →" | 兜底逃生口，避免任何卡死 |

**交互细节**（决定"专业感"的地方）：
- 手机号输入：**11 位数字键盘**，输入满 11 位自动高亮"获取验证码"
- 验证码：6 位，**60 秒倒计时**，倒计时期间按钮置灰并显示剩余秒数
- 所有网络操作有 **loading 态**，按钮变"登录中…"并禁用，**防重复点击**
- 错误提示**贴在对应输入框下方**（不是弹 Toast），例如"验证码错误，请重新输入"
- 成功后有**一次明确的过渡**（不是瞬间跳走），让用户知道"登录成功了"

#### 页面 2：`pages/ProfileSetup.ets`（新增，可选）

首次登录后引导填 3 项——**只填 3 项，且都可跳过**：

| 字段 | 控件 | 为什么问 |
|---|---|---|
| 昵称 | 文本输入 | 搭子匹配页要显示名字 |
| 在读年级 | 单选（大一/大二/大三/大四/研究生） | 影响课程与目标的默认值 |
| 本学期目标课程 | 单选/输入 | 直接影响 `/api/v1/agent/proactive` 的 `daysLeft` 与优先级 |

> 💡 **这一页是"主动服务"的数据入口**——不填，Agent 就不知道你的考试还有几天。
> 文案可以写成："**告诉我你在备考什么，我才能在对的时候提醒你。**"

#### 页面 3：`pages/Account.ets`（新增，或并入现有页面）

- 当前账号（昵称 / 手机号脱敏 `138****8888`）
- 学习数据概览（掌握度、连续学习天数、累计专注）
- **退出登录**（二次确认）
- **注销账号**（合规要求；二次确认 + 明确说明数据会删除）
- 隐私设置：位置权限开关、图片数据清理入口

### 3.3 状态覆盖（对齐项目已有的"状态规范"）

`docs/前端README.md` 已规定所有流程覆盖 **进行中 / 成功 / 无结果失败 / 下一步** 四态。登录页必须做到：

| 状态 | 表现 |
|---|---|
| **进行中** | 按钮 loading + 文案"登录中…"，输入框禁用 |
| **成功** | 明确的成功提示 + 过渡动画 + 跳首页 |
| **失败** | 具体原因（验证码错误 / 网络不可用 / 该手机号未注册）+ 「重试」按钮，**不清空已输入内容** |
| **无网络** | 明确提示 + 「**以离线模式继续**」按钮（切到 Fixture，直达首页）★ |

> ★ **"无网络也能进"这一条是本项目的特色**：因为它天然衔接到已有的离线 Fixture 模式。

### 3.4 UI 规范（直接复用现有设计语言）

```
主色        #2563EB   （主按钮、链接、强调）
圆角        12–20 vp
内边距      16–20 vp
主按钮      高 48vp，实心 #2563EB，白色 15sp 文字
次按钮      高 48vp，白底 + #BFDBFE 描边 + #2563EB 文字
文字按钮    14sp，#64748B
错误色      #EF4444
成功色      #10B981
输入框      高 44–48vp，底色 #F8FAFC，圆角 10vp
页面背景    #FFFFFF / 卡片 #F8FAFC
```

> **每页只有一个实心主按钮**——这条规范让"一键体验"成为唯一的视觉焦点，**正确**。

| 文件 | 改动 |
|---|---|

| `pages/ProfileSetup.ets` | **新增** — 首次信息完善（可跳过） |

## 4. 参赛时"用户数据库"问题怎么解决

### 4.1 先明确：这个问题**真的存在**吗？

**存在，但比想象中小。** 分三种情形：

| 情形 | 是否需要数据库 | 说明 |
|---|---|---|
| **只在模拟器/真机上演示给评委看** | ❌ **不需要** | 本地 `preferences` + 后端 JSON 足够。评委只看得到**一台设备** |
| **要做"两个真人互相匹配搭子"的双设备演示** | ✅ **需要** | 至少需要一个两台设备都能访问的共享存储 |
| **文档里承诺"可对接教务系统 / 可上架"** | ✅ **需要** | 前景评估 20 分要求"可落地路径"，没有持久化就说不通 |

> **判断**：如果 [`01`](01-下一步改进分析与建议.md) §3 的 P0 服务卡片做完了、还有余力，就做真实的数据库；
> **否则，把"数据库"做成"诚实的最小实现 + 清晰的迁移路径"**，这在答辩时同样能拿分。

### 4.2 五个候选方案对比

| 方案 | 技术栈 | 成本 | 免费 | 鸿蒙契合度 | 评委观感 | 推荐度 |
|---|---|---|---|---|---|---|
| **① 本地 `preferences`** | ArkTS 原生 | **2 小时** | ✅ 完全免费 | ⭐⭐⭐⭐⭐ | 一般（单机） | ⭐⭐⭐ 演示兜底 |
| **② AGC 云数据库 + 认证服务** | 华为云服务 | **1–1.5 天** | ✅ 有免费额度 | ⭐⭐⭐⭐⭐ **原生** | ⭐⭐⭐⭐⭐ **"用了华为生态"** | ⭐⭐⭐⭐⭐ **首选** |
| **③ 自建后端 + SQLite** | 已有 Flask 后端 | **0.5 天** | ✅ 免费 | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ 次选 |

#### 方案 ② 详解：为什么推荐 AGC

**AGC（AppGallery Connect）是华为官方的应用一站式服务平台**，提供：

- **认证服务（Auth Service）**：支持**手机号验证码登录**、邮箱、华为账号、**匿名登录**，鸿蒙 ArkTS 有官方 SDK。
  参考：[手机-登录认证-ArkTS（HarmonyOS）](https://developer.huawei.com/consumer/cn/doc/appgallery-connect-guides/agc-auth-harmonyos-arkts-login-phone-0000001631566338)
- **云数据库（Cloud DB）**：对象型数据库，鸿蒙 ArkTS 原生 SDK。
  参考：[云数据库计费说明](https://developer.huawei.com/consumer/cn/doc/appgallery-connect-Guides/agc-clouddb-price-0000001256815629)、[云数据库使用限制](https://developer.huawei.com/consumer/cn/doc/appgallery-connect-guides/agc-clouddb-restrictions-0000001127557973)

**选它的四条理由**：

1. **鸿蒙原生**——这直接**计入"鸿蒙特性"数量**（评分表里"鸿蒙技术创新性"是创新性 50 分的一部分）。
   本项目现在的鸿蒙特性是"ArkTS/ArkUI + Canvas + Preferences + PhotoViewPicker + 网络"，**技术含量偏低**；加上 AGC 认证 + 云数据库，叙事立刻变成"**端云协同的鸿蒙原生 Agent**"。
2. **零运维**——不用买服务器、不用配 HTTPS、不用管备份。**对一个 12 天内要冻结的项目，这是决定性的。**
3. **合规友好**——手机号等敏感信息由华为托管，**你不碰用户密码**，隐私合规压力大幅下降（前景评估与答辩都会问隐私）。
4. **免费额度**——开发与演示阶段的开销可忽略。**具体额度与计费规则请以官方计费页为准**（链接见上），不要凭记忆写进文档。

**风险与对策**：

| 风险 | 概率 | 对策 |
|---|---|---|
| AGC 项目创建 / 配置卡住 | 中 | **今天先去 AGC 控制台把项目建起来**，别等要用了才弄 |
| 网络受限导致演示时连不上 | 中 | **必须有离线兜底**（见 §4.4） |
| 需要企业/学校实名认证 | 低 | 个人开发者账号即可开通，提前确认 |
| SDK 版本与 6.1.1(24) 不匹配 | 中 | 在 DevEco 里按官方文档核对 SDK 版本 |

#### 方案 ③ 详解：如果想自建（次选）

本工程**已经准备好这条路**：

```python
# app/repositories/sqlite_repository.py 已存在，实现了同一套 Repository 协议
# app/__init__.py 只需改一行：
repository = SqliteRepository(path)   # 原来是 JsonRepository(path)
```

**推荐做法**（成本最低、风险最低）：

1. **存储**：SQLite 单文件（`data/zhixue.db`）。演示场景完全够用，**不需要 MySQL**。
2. **认证**：不自己做密码体系。用"**昵称 + 服务端下发 UUID**"即可：
   - `POST /api/v1/auth/register { nickname }` → 返回 `{ userId, token }`
   - `POST /api/v1/auth/login { userId, token }` → 校验
   - token 存 `preferences`，请求头带 `Authorization: Bearer <token>`
3. **表结构**：见 §5。

> ⚠️ **红线**：**绝对不要自己实现密码存储**。如果一定要密码，必须用 `bcrypt`/`argon2` 加盐哈希。
> 但本项目的场景**根本不需要密码**——用 UUID + token 更简单也更安全。

## 5. 数据库设计（如果决定做真库）

### 5.1 实体关系

```
users ─1:1─ learner_profiles ─1:N─ mastery_records
  │                │
  │                └─1:N─ evidence
  │
  ├─1:N─ plans ─1:N─ plan_tasks
  │
  ├─1:N─ workflows ─1:N─ trace_events
  │
  ├─1:N─ exercise_submissions
  │
  ├─1:N─ chat_messages
  │
  ├─1:N─ focus_sessions
  │
  └─N:M─ partner_matches ──► users (对端)
```

### 5.2 表结构（SQLite 版，可直接用）

```sql
-- 用户主表：只放身份，不放学习数据（职责分离，便于换认证方式）
CREATE TABLE users (
  user_id       TEXT PRIMARY KEY,          -- UUID
  nickname      TEXT NOT NULL,
  avatar        TEXT,
  grade         TEXT,                      -- 大一/大二/...
  auth_provider TEXT NOT NULL DEFAULT 'guest',  -- guest | agc_phone | agc_anonymous
  auth_subject  TEXT,                      -- AGC 返回的 uid（不存手机号明文）
  created_at    TEXT NOT NULL,
  last_login_at TEXT,
  status        TEXT NOT NULL DEFAULT 'active'  -- active | deactivated
);
CREATE UNIQUE INDEX idx_users_auth ON users(auth_provider, auth_subject);

-- 学习画像：版本化，与后端 ProfileResponse 的 profileVersion 对应
CREATE TABLE learner_profiles (
  user_id                TEXT PRIMARY KEY REFERENCES users(user_id),
  goal                   TEXT,
  exam_date              TEXT,
  free_time_slots        TEXT,             -- JSON 数组
  profile_version        INTEGER NOT NULL DEFAULT 1,
  updated_at             TEXT NOT NULL
);

-- 掌握度：一个用户 × 一个知识点一行
CREATE TABLE mastery_records (
  user_id              TEXT NOT NULL REFERENCES users(user_id),
  knowledge_point_id   TEXT NOT NULL,
  knowledge_point_name TEXT NOT NULL,
  mastery_score        REAL NOT NULL DEFAULT 0,   -- 0..100
  confidence           REAL NOT NULL DEFAULT 0,
  last_updated         TEXT NOT NULL,
  PRIMARY KEY (user_id, knowledge_point_id)
);

-- 学习证据：掌握度变化的依据（对应 Evidence 模型）
CREATE TABLE evidence (
  evidence_id        TEXT PRIMARY KEY,
  user_id            TEXT NOT NULL REFERENCES users(user_id),
  source_type        TEXT NOT NULL,        -- exercise | focus | chat
  source_id          TEXT NOT NULL,
  knowledge_point_id TEXT,
  metric             TEXT NOT NULL,
  value              REAL NOT NULL,
  reliability        REAL NOT NULL DEFAULT 1,
  timestamp          TEXT NOT NULL
);
CREATE INDEX idx_evidence_user ON evidence(user_id, timestamp DESC);

-- 学习计划与任务
CREATE TABLE plans (
  plan_id                        TEXT PRIMARY KEY,
  user_id                        TEXT NOT NULL REFERENCES users(user_id),
  version                        INTEGER NOT NULL DEFAULT 1,
  generated_from_profile_version INTEGER NOT NULL,
  reason                         TEXT,
  created_at                     TEXT NOT NULL
);
CREATE TABLE plan_tasks (
  plan_id              TEXT NOT NULL REFERENCES plans(plan_id),
  task_id              TEXT NOT NULL,
  knowledge_point_id   TEXT NOT NULL,
  knowledge_point_name TEXT NOT NULL,
  duration_minutes     INTEGER NOT NULL,
  status               TEXT NOT NULL DEFAULT 'pending',
  priority             TEXT,
  PRIMARY KEY (plan_id, task_id)
);

-- 练习提交：idempotency_key 建唯一索引 = 幂等保证落在数据库层
CREATE TABLE exercise_submissions (
  submission_id   TEXT PRIMARY KEY,
  user_id         TEXT NOT NULL REFERENCES users(user_id),
  set_id          TEXT NOT NULL,
  idempotency_key TEXT NOT NULL,
  score           REAL NOT NULL,
  old_mastery     REAL,
  new_mastery     REAL,
  need_replan     INTEGER NOT NULL DEFAULT 0,
  created_at      TEXT NOT NULL
);
CREATE UNIQUE INDEX idx_submission_idem ON exercise_submissions(user_id, idempotency_key);

-- 对话历史
CREATE TABLE chat_messages (
  message_id  TEXT PRIMARY KEY,
  user_id     TEXT NOT NULL REFERENCES users(user_id),
  session_id  TEXT NOT NULL,
  role        TEXT NOT NULL,               -- user | assistant
  text        TEXT NOT NULL,
  intent      TEXT,
  created_at  TEXT NOT NULL
);
CREATE INDEX idx_chat_user ON chat_messages(user_id, created_at DESC);

-- 专注会话
CREATE TABLE focus_sessions (
  session_id      TEXT PRIMARY KEY,
  user_id         TEXT NOT NULL REFERENCES users(user_id),
  task_id         TEXT,
  course_name     TEXT,
  planned_minutes INTEGER NOT NULL,
  actual_minutes  INTEGER NOT NULL DEFAULT 0,
  pause_count     INTEGER NOT NULL DEFAULT 0,
  status          TEXT NOT NULL,          -- completed | not_completed | interrupted
  self_rating     TEXT,
  started_at      TEXT NOT NULL,
  ended_at        TEXT
);

-- 搭子匹配：双向存两条，便于"我邀请的人"和"邀请我的人"分开查
CREATE TABLE partner_matches (
  match_id     TEXT PRIMARY KEY,
  user_id      TEXT NOT NULL REFERENCES users(user_id),
  peer_user_id TEXT NOT NULL REFERENCES users(user_id),
  total_score  REAL NOT NULL,
  factors      TEXT NOT NULL,              -- JSON：四因子明细
  status       TEXT NOT NULL DEFAULT 'suggested', -- suggested | invited | accepted | declined
  created_at   TEXT NOT NULL,
  UNIQUE (user_id, peer_user_id)
);

-- Agent 决策轨迹（对应 TraceEvent）
CREATE TABLE trace_events (
  event_id       TEXT PRIMARY KEY,
  trace_id       TEXT NOT NULL,
  user_id        TEXT NOT NULL REFERENCES users(user_id),
  agent          TEXT NOT NULL,
  tool_calls     TEXT NOT NULL,            -- JSON 数组
  input_summary  TEXT,
  output_summary TEXT,
  evidence_ids   TEXT,                     -- JSON 数组
  state_version  INTEGER NOT NULL,
  status         TEXT NOT NULL,
  timestamp      TEXT NOT NULL
);
CREATE INDEX idx_trace ON trace_events(trace_id, state_version);
```

### 5.3 三条设计纪律

1. **`users` 表只放身份，不放学习数据**。这样将来从 AGC 认证换成自建认证，只动 `users` 表。
2. **`idempotency_key` 的唯一索引必须建在数据库层**。后端已有幂等逻辑（实测"同 key 重放响应逐字节一致"），数据库唯一索引是它的**第二道保险**——并发重复提交时不会双写。
3. **不要存手机号明文**。存 AGC 返回的 `uid`（`auth_subject`），需要展示时脱敏。**这是隐私合规的底线，也是答辩加分点。**

## 6. 登录接口契约（建议，已对齐 v0.3 风格）

```yaml
POST /api/v1/auth/register
  body: { "nickname": "小明", "grade": "大二" }
  200:  { "userId": "u-8f3a...", "token": "eyJ...", "profileVersion": 1 }

POST /api/v1/auth/login
  body: { "userId": "u-8f3a...", "token": "eyJ..." }
  200:  { "userId": "u-8f3a...", "nickname": "小明", "token": "eyJ..." }
  401:  { "errorCode": "UNAUTHORIZED", "message": "登录已失效，请重新登录", "details": null }

POST /api/v1/auth/logout
  200:  { "status": "ok" }

DELETE /api/v1/auth/account
  200:  { "status": "deactivated" }   # 合规要求：账号注销

GET  /api/v1/auth/me
  200:  { "userId": "...", "nickname": "...", "grade": "...", "createdAt": "..." }
```

**鉴权头**（生产化后所有 `/api/v1` 都要校验）：

```
Authorization: Bearer <token>
```

> ⚠️ **契约纪律**：新增接口必须先改 `contracts/openapi.json`，**再**改代码。
> 本项目已有静态护栏校验两份 `openapi.json` 逐字节一致，改一处必须同步另一处。

### 一页速查

> **登录界面**：轻量三入口（一键体验 / 手机号 / 昵称），游客优先，绝不硬门禁。
> **适配度**：技术适配度很高（模型、契约、UI 语言都现成），但**必须先统一用户 ID**，且**对 50 分创新性几乎无贡献**。
> **用户数据库**：首选 **AGC 云数据库 + 认证服务**（鸿蒙原生、零运维、顺带拿鸿蒙特性）；次选**已有后端 + SQLite 换一行**；**12 天窗口下，若 P0 未完成，就用本地 `preferences` + 诚实写明迁移路径**。
> **一句话**：**先把"会主动找你的 Agent"做出来，再给它装一个门牌号。**

### 关于数据库：为什么这次没有换掉 JSON

原方案建议换 SQLite 或 AGC。实际实现选择**继续用 `JsonRepository`**，理由是：

1. **单文件、零运维、零配置**——评测现场不会因为数据库文件锁或驱动问题翻车。
2. **仓储层已抽象**——`app/repositories/repository.py` 定义了 `Repository` 协议，
   `sqlite_repository.py` 也已实现同一套接口。切换只需改 `create_app()` 里的一行：
   `repository = SqliteRepository(path)`。
3. **用户数据已经按集合分片**——新增的 `users` / `sessions` 是两个独立集合，
   与 `profiles` / `plans` 并列，结构上已经是"多用户"的，只是物理上还在同一个 JSON 文件里。

**迁移路径已写在本文档 §4.2 与 §5**，需要在文档中向评委说明"演示用单文件、生产化换 AGC/SQLite"。
