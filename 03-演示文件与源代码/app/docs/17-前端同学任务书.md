## 二、P0-2：验证 token 加密真的生效（1 小时）🔴 风险最集中

### 2.1 我改了什么

`AuthStore.ets` 原先把 token **明文**写进 preferences：

```typescript
store.putSync(AuthStore.KEY_TOKEN, session.token);   // 明文
```

preferences 在应用私有目录，未 root 的机器上外部读不到，但它**不是安全存储**：
备份、调试桥、任何拿到沙箱的途径都能读出明文 token，而 token 等同账号
（有效期 30 天）。

**现在**：新增 `api/TokenCipher.ets`，token 经 **AES-256-GCM**（每条消息独立 nonce）
加密后落盘，**数据密钥**托管在系统**资产库**（Asset Store Kit）。

### 2.2 已确证的部分（有官方文档 + 本机 d.ts 双重依据）

| 用法 | 依据 |
|---|---|
| `createCipher('AES256\|GCM\|NoPadding')` | AES 一律三段式；GCM 属流模式，填充模式等价 |
| `Cipher.initSync(opMode, key, params)` **三参数** | `@ohos.security.cryptoFramework.d.ts:3551` |
| `createSymKeyGenerator('AES256')` | 密钥生成规格里 AES 只有"算法+长度"两段，不带分组模式 |
| `convertKeySync({data: 32字节})` | d.ts `:2006`；AES256 **必须正好 32 字节** |
| 加密后从 `doFinalSync` 输出**末尾取 16 字节**作 tag | 官方 GcmParamsSpec 表原文（4 个修订版一致） |
| **解密时 tag 只走 `spec.authTag`，不能拼进 data** | 官方 FAQ 把 key/iv/aad/tag/ciphertext 列为**5 个独立输入** |
| `asset.Tag.RETURN_TYPE = ReturnType.ALL` | 不设它 `query` **不返回 SECRET** |
| `CONFLICT_RESOLUTION = ConflictResolution.OVERWRITE` | d.ts `:927`/`:1513`；默认 `THROW_ERROR`(`:941`) |

> 完整报告（含全部 d.ts 行号与文档原文引证）：
> `docs/20-token加密API核验报告.md`

> ⚠️ **顺便记一笔**：那份报告抓出了我第一版的一个 **P0 bug** ——
> 我把密文与 tag **拼接**后传给 `doFinalSync`。GCM 的 tag 是对
> `AAD ‖ ciphertext` 计算的，解密时算法库会拿喂进去的**全部字节**当密文重算 tag，
> 于是必然校验失败 → `decrypt()` **永远返回 `null`** →
> **所有已登录用户每次冷启动都被当成未登录**。已修正为只传纯密文。

### 2.3 ⚠️ 仍有一处未实测

**「`doFinalSync(明文)` 一次调用（不走 `update`）在所有情况下都返回 `密文‖tag`」**
—— 官方示例只演示了 `update + doFinal(null)`；"末尾 16 字节是 tag"来自
API 参考表格约定。本机无设备可实测。

**若要 100% 对齐官方示例**，把加密侧改成：

```typescript
cipher.initSync(cryptoFramework.CryptoMode.ENCRYPT_MODE, key, spec);
const cipherText: Uint8Array = cipher.updateSync({ data: plainBytes }).data;
const authTag: Uint8Array = cipher.doFinalSync(null).data;   // 此时恰好 16 字节，无需切片
```

这样不依赖"末 16 字节"的约定。

### 2.4 兜底已就位（不会把登录打挂）

`AuthStore.encodeToken()` 在加密失败时会**降级为明文**并把
`encryptionDegraded()` 置为 `true`，由账号页如实提示。
**即使上述约定有偏差，应用仍能正常登录**，只是退回改动前的存储强度。

### 2.5 要做什么

1. 真机上**登录一次 → 杀进程 → 重开**，确认**仍是登录态**
2. 若变成未登录：看 hilog 里 `TokenCipher` 的 warn
   （`crypto_init_failed:xxx` 或 `encrypt failed:xxx`）
3. 若确认是 tag 切片问题 → 按 §2.3 改成 `updateSync + doFinalSync(null)`
4. 确认无问题后，把 `TokenCipher.ets` 文件头里"仍未在本机验证的部分"一段删掉

**验收**：

- [ ] 冷启动后仍为登录态
- [ ] hilog 里**无** `TokenCipher` 的 warn
- [ ] 归档冷启动前后截图 + hilog 片段

### 2.6 仍然存在的边界（不夸大）

密钥是**软件密钥**，不是 HUKS 硬件密钥。HUKS 的密钥不出安全区、安全性最高，
但其 `initSession`/`finishSession` 需要多轮异步交互，与 `AuthStore` 的**同步**
preferences 范式不兼容，混用会引入"写了一半"的状态。
因此选择"软件密钥 + 系统资产库托管"，并在文档里如实写明这条边界。
