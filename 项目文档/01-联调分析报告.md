## 三、【本轮新发现】pytest 会污染交付包的对话历史文件

### 3.1 缺陷

`chat/history.json` 的可写路径**写死在** `chat_llm._CHAT_DIR`：

```python
_CHAT_DIR = _BASE_DIR.parent.parent / "chat"
def _history_path() -> Path:
    return _CHAT_DIR / "history.json"
```

而 `data/repository.json` **早就有** `ZHIXUE_REPOSITORY` 重定向（我 liantiao4 加的），
`integration/run_liantiao5.py` 也一直用它把联调数据写到临时文件。

**但 `history.json` 没有对应的重定向机制**，于是：

* `tests/test_technical_improvements.py` 里有几个用例会真的走
  `POST /api/agent/chat` 与 `DELETE /api/agent/history`
* **每跑一次 pytest，交付包的 `chat/history.json` 就被写一次**

### 3.2 受控实验（不是推断）

我把文件清成 `{"demo-user": []}`（23 B），然后**分别**单独执行：

```
复位后          23 B     分桶={'demo-user': 0}
只跑 pytest   1,100 B    分桶={'demo-user': 2, 'user-a': 0, 'user-b': 1}   ← pytest 写的
只跑联调      1,100 B    不变（联调已重定向）                        ← 联调是干净的
```

**结论明确：污染源是 pytest，不是联调。**

### 3.3 队友交付物里的实际后果

队友那份 `chat/history.json` 是 **18,162 B / 5 个分桶**：

```
demo-user / user-a / user-b / probe-a / probe-b
```

对比干净状态只需 `demo-user` 一个桶。**这就是反复跑测试累积出来的。**

### 3.4 修复（三处）

1. **`chat_llm` 支持重定向**：

```python
def _var_dir() -> Path:
    override = (os.getenv("ZHIXUE_CHAT_DIR") or "").strip()
    return Path(override) if override else _CHAT_DIR

def _history_path() -> Path:
    directory = _var_dir()
    directory.mkdir(parents=True, exist_ok=True)
    return directory / "history.json"
```

   **只重定向可写文件**；`prompts/` 与 mock 数据是只读资源，仍从包内读，交付包保持自足。

2. **`integration/run_liantiao5.py`** 同时设 `ZHIXUE_REPOSITORY` 与 `ZHIXUE_CHAT_DIR`

3. **`tests/conftest.py`** 新增 autouse fixture，把测试的历史重定向到
   会话级临时目录（用 `tmp_path_factory` 而非 `tmp_path`——
   后者是函数级，会让"跨用例累积"类断言失效）

### 3.5 验证

新增 `tests/test_chat_history_redirect.py`（**9 项**）固化：

| 测试 | 断言 |
|---|---|
| `test_history_path_falls_back_to_packaged_dir` | 未设变量时回落到包内（交付包自足） |
| `test_history_path_honours_override` | 设了就跟随，且目录自动创建 |
| `test_blank_override_falls_back` | 空白串不算有效覆盖 |
| `test_append_does_not_touch_packaged_history` | **核心回归**：append 不碰包内文件 |
| `test_clear_does_not_touch_packaged_history` | **核心回归**：clear 不碰包内文件 |
| `test_clear_missing_key_is_noop_and_creates_no_file` | 对不存在的键 clear 是无副作用的 no-op |
| `test_redirected_writes_are_readable_back` | 重定向后读写一致 |
| `test_readonly_resources_still_come_from_package` | `prompts/` 不被误重定向 |
| `test_history_file_is_keyed_by_user` | 分桶语义在重定向下不变 |

**修复后实测**：

```
跑完 295 项测试后，交付包 chat/history.json = 23 B，分桶 ['demo-user']   ✅ 未被写入
```

### 3.6 同一根因的第二处：`mock_wrong_questions.json` 也在被污染

顺着 `history.json` 的线索复查，发现**同一份缺陷还有第二个受害文件**。

`_handle_analyze_wrong()` 在错题分析完成后会把结果 append 回文件：

```python
questions = _load_json("mock_wrong_questions.json", [])
if isinstance(questions, list):
    questions.append(analysis)
    (_CHAT_DIR / "mock_wrong_questions.json").write_text(...)   # ← 又写死了 _CHAT_DIR
```

**实测证据**：

| 版本 | 项数 | 大小 |
|---|---|---|
| 队友交付 | **26 项** | 34,265 B |
| 基线（liantiao4） | 15 项 | 20,117 B |

多出的 11 项特征非常明显：

```
qid=u001_UUID                              ×4   ← 字面量 "UUID" 没被替换
qid=u001_6a8d4f3e-1c2b-4e9a-8f7d-5b2c3d4  ×7
   图片=None  我的答案=None  正确=None
   知识点=['二叉树遍历','递归理解']   ← 11 项完全一样
```

即**同一份测试用的合成数据被重复追加了 11 次**，且 `input` 字段全空 —— 不是真实数据。

**修复**：新增 `_mutable_path()`，并把 `_load_json()` 改成
**重定向目录优先、回落包内**：

```python
def _load_json(filename, default=None):
    for directory in (_var_dir(), _CHAT_DIR):   # 重定向优先，包内兜底
        path = directory / filename
        if path.exists():
            ...

def _mutable_path(filename) -> Path:
    """会被写入的数据文件；首次写入前从包内播种初值。"""
```

**为什么要"播种"**：`mock_wrong_questions.json` 既是**演示数据**又是**运行期可写**。
如果重定向目录里直接空白起步，演示数据就丢了；所以首次写入前先从包内复制一份，
之后只改重定向那份。

**已清回基线**：liantiao5 采用 15 项 / 20,117 B 的干净版本。

**新增回归测试**（`tests/test_chat_history_redirect.py`，共 **15 项**）：

| 测试 | 断言 |
|---|---|
| `test_load_json_prefers_redirected_dir` | 读顺序：重定向优先、回落包内 |
| `test_mutable_path_seeds_from_package` | 首次写入前从包内播种 |
| `test_mutable_path_does_not_overwrite_existing` | 已存在的重定向文件不被覆盖 |
| `test_wrong_question_write_does_not_touch_packaged_file` | **核心回归**：错题落盘不碰包内 |

### 3.7 修复后的三份数据文件（联调前后逐字节一致）

```
联调前                                  联调后
chat/history.json              23 B  →  23 B      sha 不变
chat/mock_wrong_questions.json 20,117 B → 20,117 B sha 不变
data/repository.json           37,376 B → 37,376 B sha 不变
```

**联调与测试都不再改动交付包的任何数据文件。**

### 6.2 契约合并的关键判断

队友的前端契约 `contracts/openapi.json` 是 **79,080 B**，我的是 **82,149 B**。
按 schema 名与端点数都一样（28 / 51），**但字节数差 3 KB**。

我做的是**字段级比对**而不是"看谁大用谁"：

```
字段路径数：源前端 1080   liantiao4 1080
源前端独有: 0 条
liantiao4 独有: 0 条
同路径但取值不同: 0 处
```

**结论：纯格式差异，语义完全相同。** 已统一为 canonical 格式
（`json.dumps(ensure_ascii=False, indent=2)`）并同步镜像，两份 **82,149 B 逐字节一致**。

> 这一步很重要：如果直接按大小选，会丢掉一方的格式一致性；
> 如果直接报"契约不一致"，会误判成联调阻塞。**逐字段比对才给出正确判断。**
