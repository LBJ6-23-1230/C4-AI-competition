## 二、P1-1：~~修 `maxSteps=1` 时 `for/else` 误标~~ —— **已查证不存在，已回退**（无需你做）

> **这一节原本是给你的任务，现在撤销。** 保留记录是为了说明清楚结论，
> 避免下一个人重复我这次的弯路。

### 2.1 结论：那个缺陷不存在

我一度认为 `app/runtime/loop.py` 的 `for ... else` 会在 `max_steps` 恰好用满时
把正常结束误标 `status=error`，并**据此改了代码、写了回归测试**。

**系统实测后结论相反**：

1. **`finish` / `waiting` 恰好落在最后一次迭代时不会误标** ——
   这两条出口各自都带 `break`，`for ... else` 的 `else` 只在"循环未被 `break`"时执行。
2. **`else` 是可达的，而且在那种情形下报错是对的** ——
   跑满 `max_steps` 仍未进入终态，就是真的超限（`max_steps=1` + 只走了一个普通步）。
3. **我的"修复"反而真的弄坏了 `waiting` 场景** ——
   `waiting` 分支把 status 写成 `"running"`，我改用"循环后按 `session.status` 判定"
   之后，**正常等答题被误判成 `max_steps` error**
   （对照实验：改写版 1 例误判 / 原版 0 例）。

### 2.2 已做的处理

- **完全回退** `run_workflow`：字节码与改动前**逐指令一致**
  （`co_code` 相同、325 条指令序列相同；只有 docstring 文本不同）
- 在 docstring 里写明了 `else` 可达的原因与这次误判的经过
- 新增 6 项测试把**真实边界行为**固化
  （`tests/test_technical_improvements.py`）：
  - `finish` 落最后一次 → `completed`，不报 error
  - `waiting` 落最后一次 → 保持 `running`，不报 error
  - 真跑满步数 → 如实报 `max_steps` error
  - 已终态会话 → 立即返回，不新增状态版本
  - 等答题状态 → 短路返回，不推进

### 2.3 你不需要做任何事

**保持现状即可。** 唯一要注意的是：
**改任何"看起来可疑"的控制流之前，先用受控实验把行为测出来，
不要凭语义直觉下结论** —— 这正是我这次踩的坑。

## 五、P2 事项

### ✅ P2-1a `405` / `414` / `415` / `413` 统一 JSON —— **本轮已完成**

已在 `app/__init__.py` 为这四个状态码各注册 JSON 处理器，
统一返回 `{errorCode: "BAD_REQUEST", message, details}`。

验证：`tests/test_technical_improvements.py` 4 项 + 联调 2 项：

```
[PASS] 方法不允许 → 405 且返回 JSON errorCode  | HTTP 405 body=dict
[PASS] 非 JSON 请求体 → JSON 400（不是 HTML 错误页）  | HTTP 400 body=dict
```

> **一个诚实的说明**：`test_client` **不会触发 414** ——
> 414 是 WSGI/HTTP 服务器层判定的（请求行长度上限），Flask 测试客户端
> 不施加该限制。所以 414 的处理器是"直接调用处理器"测的，**真实触发未覆盖**。
> 已列入 `19-未完成事项清单.md`（A11，优先级很低：前端几乎不会发超长 URL）。

### ✅ P2-1b CORS 收敛 —— **本轮已完成**

原先裸 `CORS(app)` 反射任意 `Origin`。现在改成白名单正则，
只放行本机开发与**私有网段**（HarmonyOS 真机走局域网 IP，不能误伤），
可用 `ZHIXUE_CORS_ORIGINS` 覆盖。

```
[PASS] CORS 不反射任意 Origin（原先裸 CORS(app)）  | Access-Control-Allow-Origin=None
[PASS] CORS 仍放行本机开发来源（收紧不能误伤联调）  | Access-Control-Allow-Origin='http://localhost:8080'
```

`test_cors_allows_private_lan_origin_for_real_device` 还专门覆盖了
`http://192.168.1.20:5000`。

### ✅ P2-2 `/api/agent/history` 用户隔离 —— **本轮已完成**

原先 `chat/history.json` 是**一个全局 JSON 数组**，所有用户混在一起：
`GET` 返回**所有人的聊天记录**，`DELETE` 会**清空所有人**。

现在按 `userId` 分桶（`{ "demo-user": [...], "u-xxxx": [...] }`），
身份走统一的 `resolve_user_id()`，响应回传 `userId`，
并**兼容旧的扁平数组格式**（一次性归给 `demo-user`，老数据不丢）。

```
[PASS] 对话历史按用户隔离（甲只看得到自己的）  | 甲的历史=['甲的问题']
[PASS] 清理甲的历史不影响乙（原先 DELETE 会清空所有人）  | 乙的历史=['乙的问题']
```

### ✅ P2-2b 联调污染交付包 —— **本轮已完成**

见下方"硬规则 2"。实测**联调前后交付包变化 0 B**。

### P2-3 双进程并发写库（2 小时，非阻塞）

**这条现在有了更好的答案**：本轮已实现 **SQLite 可选后端**，
它从根上解决了这个问题（每次只写一行，并发由数据库保证，
`busy_timeout=15s` + WAL 模式）。

```powershell
$env:ZHIXUE_DB="sqlite"; python run.py          # 用 <数据目录>/repository.sqlite
$env:ZHIXUE_DB="sqlite:E:\temp\data.sqlite"     # 指定路径
```

实测吞吐对照（`save×200`）：**JSON 1640.9 ms vs SQLite 13.1 ms（约 125 倍）**，
且 **JSON 单次 save 随数据量线性增长**（50 条 5.6ms → 800 条 52.4ms），
SQLite 恒定 ~0.03ms。

**建议**：如果确定要多进程部署，就把 `ZHIXUE_DB` 设为 `sqlite`；
单进程演示保持默认 `json`（JSON 文件可直接肉眼查看，便于答辩核对）。
无论选哪个，**在 README 里写明部署形态**。
