## 一、直接回答：接入了，而且是"两条通路"

后端确实接入了大模型 API，且**不是单点接入，而是两条独立通路**：

| 通路 | 文件 | 用途 | SDK |
|---|---|---|---|
| **A. 自然语言层** | `app/agent/chat_llm.py` | `/api/agent/chat`：意图识别 + 6 路子 Agent + **Qwen-VL 多模态识图** | `openai` 包（OpenAI 兼容协议） |
| **B. 工作流决策层** | `app/model_adapters/qwen_adapter.py` | 工作流里「下一步叫哪个 Agent」的决策 | 标准库 `urllib`（不用 SDK） |

**Provider**：通义千问 / DashScope（`https://dashscope.aliyuncs.com/compatible-mode/v1`），
协议是 OpenAI 兼容格式，因此**换 DeepSeek 只需改两个环境变量**（`.env.example` 里已写好备选配置）。

### 设计纪律（值得写进答辩）

`chat_llm.py` 文件头写得很清楚：

> 1. LLM 只负责"生成自然语言回复 / 识别意图"；**所有业务计算（判分、掌握度、优先级、重规划）
>    一律留在 `app/tools` 与 `app/decision` 的确定性代码里，不进入 prompt**。
> 2. 未配置 `DASHSCOPE_API_KEY` 时**不得伪装成真实 LLM 结果**。

这个边界划得很干净：**模型只做它擅长的（自然语言、意图、看图），算分交给确定性代码。**
所以「拔掉大模型依然能走完主链」这个结论是成立的。

## 四、🔴 发现并修复的真缺陷：多模态识图链路**不可达**

### 现象

即使配好 Key，**错题拍照识图（Qwen-VL）也永远不会被调用**。

### 根因

`app/api/chat.py` 在"只有图片没有文字"时，会把消息替换成占位句：

```python
if not message and image_base64:
    message = "帮我分析这道题"
```

而 `app/agent/chat_llm.py` 的意图识别**只看文本，看不到图片**：

```python
intent, llm_used = detect_intent(message)      # ← 没有 image 参数
```

关键词表里 `analyze_wrong` 的词是：

```python
("analyze_wrong", ("这道题", "错题", "为什么错", "图片", "拍照")),
#                 ↑ 是"这道题"，不是"分析这道题"
```

`"帮我分析这道题"` 里**没有**"这道题"这个连续子串（中间隔着"分析"），
于是落到最后一条 → `get_suggestion`。

**结果**：`intent != analyze_wrong` → `_handle_analyze_wrong()` 不执行
→ **`_call_llm_with_image()` 这条 Qwen-VL 链路一次都不会跑**。

### 实测证据（修复前）

我传了图片，假模型收到的请求里 `has_image=False`：

```
model=qwen-vl-plus temp=0    has_image=False  sys='你是一个严格的学习助手意图识别器…'
model=qwen-vl-plus temp=0.7  has_image=False  sys='你是一个贴心的学习助手"小艺"…'
intent : get_suggestion        ← 应该是 analyze_wrong
```

**`_call_llm_with_image()` 在代码里写得很完整，但生产路径上永远走不到。**

### 修复

```python
def detect_intent(message: str, has_image: bool = False) -> tuple[str, bool]:
    # 用户上传了错题图片，意图毫无歧义就是"分析这道题"。
    # 带图即错题，既省一次模型调用，又让多模态路径真正可达。
    if has_image:
        return "analyze_wrong", True
    ...原有文本逻辑不变...
```

```python
intent, llm_used = detect_intent(message, has_image=bool(image_base64))
```

### 修复后实测

```
=== 修复后：带图片的对话 ===
  llmUsed: True  intent: analyze_wrong
  reply  : '【假模型·多模态】已收到图片并识别出知识点：二叉树后序遍历。'

=== 假模型收到的请求 ===
  model=qwen-vl-plus temp=0.7 has_image=True      ← 图片真的传进去了
```

**只发了 1 次请求**（修复前发 2 次）——省掉了一次无意义的文本意图识别。

## 五、⚪ 附带发现（未修，建议知悉）

### 5.1 两条通路的默认模型不一致

| 位置 | 默认值 |
|---|---|
| `chat_llm.py` | `qwen-vl-plus`（多模态） |
| `qwen_adapter.py` | `qwen-plus`（纯文本） |
| `.env.example` | `qwen-vl-plus` |

**影响**：如果部署时**只填 Key、不写 `LLM_MODEL`**，聊天层用多模态模型、
工作流决策层用纯文本模型。功能上都能跑（决策不需要看图），但**不够一致**。

**建议**：把 `qwen_adapter.py` 的默认值也改成 `qwen-vl-plus`，或统一读一个常量。

### 5.2 `.env` 加载路径（已排查，**不是问题**）

`QwenAdapter.from_environment()` 用的是 `load_dotenv()`（无参数），
理论上依赖当前工作目录。我实测了两种情况：

| 启动位置 | 结果 |
|---|---|
| 从 `server/zhixue-agent-server/` 启动（正常用法） | ✅ 读到 Key，model=qwen-vl-plus |
| 从工作区根目录启动（异常用法） | ✅ 也读到了 |

`python-dotenv` 会自动向上查找，所以两种方式都正常。**无问题。**

### 5.3 `LLM_TIMEOUT_SECONDS` 两条通路都生效

* 聊天层：`_client()` 传 `timeout=llm_timeout_seconds()`
* 工作流层：`QwenAdapter` 用 `ThreadPoolExecutor` + `future.result(timeout=...)` 双重保护

设计合理。

## 七、答辩可用的话术

> **「模型和计算是分开的」**
> "我们不把判分、掌握度、优先级这些交给大模型——它们是确定性代码，可复现、可验证。
> 模型只做三件事：听懂用户意图、生成自然语言回复、看错题图片。
> 所以**拔掉大模型我们照样能走完整个学习闭环**，只是回复变成规则模板。"
>
> **「降级是诚实的」**
> "没配 Key 时，接口返回 `llmUsed: false`，界面上直接显示「本地规则兜底」——
> 我们不做黑盒包装，用户和评委都能看出这次到底是谁在回答。"
>
> **「换模型成本很低」**
> "我们走 OpenAI 兼容协议，换 DeepSeek 只需要改 `.env` 里两个变量，代码一行不动。"
