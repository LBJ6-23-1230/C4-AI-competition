# 签名材料核验报告（发布 Profile）

> 核验时间：2026-09-21
> 核验对象：AGC 下载的 `zhixue-release.cer` + `zhixue-release-profileRelease.p7b`
> 核验方式：直接解析 PKCS#7 / X.509 结构，逐字节比对公钥
> **核验结论：配套 ✅ 可以进 DevEco 配置签名**

### 逐项判读

| 字段 | 值 | 判读 |
|---|---|---|
| `type` | `release` | ✅ **发布类型**，正确 |
| `bundle-name` | `com.zhixue.mate` | ✅ 与工程一致 |
| `app-identifier` | `6917617022690149565` | ✅ 与 AGC APP ID 一致 |
| `validity.not-after` | `1884697583` → **2029-09-21** | ✅ 3 年有效期 |
| `issuer` | `app_gallery` | ✅ 应用市场发布渠道 |
| `apl` | `normal` | ✅ 普通应用级别 |
| **设备白名单** | **`device-ids` / `debug-info` 字段均不存在** | ✅ **发布 Profile 本就不绑设备** |
| `acls.allowed-acls` | `[]` | ✅ 未申请受限权限（不需要） |

> **最重要的一条**：Profile 里**没有任何设备 ID 字段**。这从密码学层面证实了「发布 Profile 不绑设备」——也就是"不借手机也能签出 HAP"这条路线成立。

## 二、配套性核验（关键结论）

### 2.1 三份材料

| 材料 | 内容 |
|---|---|
| `zhixue-release.p7b` | 发布 Profile，内嵌一张 `distribution-certificate` |
| `zhixue-release.cer` | 3 段证书链（PEM） |
| `zhixue-debug.p12` | 私钥库（含密钥对） |

### 2.2 Profile 内嵌证书

```
subject : 许梓恒(2044548867596244609)\Release
issuer  : Huawei CBG Developer Relations CA G2
serial  : 09FD49ABAEBFC1F93BB4E667D8AC
有效期  : 2026-09-21 ~ 2029-09-21
SKI     : 6F:62:09:DF:2D:14:95:A0:4D:2F:88:CB:E8:98:16:B1:06:14:8C:B9
```

### 2.3 本地 `release.cer` 证书链

| 段 | 角色 | SKI | 公钥 BIT STRING sha256 |
|---|---|---|---|
| `[0]` | leaf | `A38E5AF5...DC2000` | `EE:C9:FE:81:BD:4F:CC:B0...` |
| `[1]` | 中间 CA | `DB5E93B2...7FF35E` | `B4:9A:84:1F:5F:16:4D:F5...` |
| `[2]` | 根 | **`6F6209DF...148CB9`** | **`A6:22:8E:48:73:71:42:E4...05:3D`** |

### 2.4 比对结果

| 比对项 | 结果 |
|---|---|
| Profile 证书 SKI **vs** `release.cer[2]` SKI | **完全相同** `6F:62:09:DF:...:06:14:8C:B9` |
| Profile 证书公钥 sha256 **vs** `release.cer[2]` 公钥 sha256 | **完全相同** `A6:22:8E:48:...:88:05:3D` |
| Profile 证书公钥 **vs** `release.cer[0]`（leaf） | 不同 |

> ### ✅ 结论
> **Profile 绑定的证书 = 本地 `zhixue-release.cer` 链中 SKI 为 `6F62...8CB9` 的那一张。**
> 公钥逐字节一致 —— 配套关系成立，DevEco 手动签名可以走通。

## 三、DevEco 签名配置（照填）

**File → Project Structure → Signing Configs**

1. **⚠️ 取消勾选 `Automatically generate signature`**
   （自动签名会重新生成材料、随机化 `appid`，打断小艺与华为账号的授权关系）
2. 点 `+` 新建配置，命名 `release`：

| 字段 | 填什么 |
|---|---|
| Store file (.p12) | `E:\zhixue-signing\zhixue-debug.p12` |
| Store password | 你创建 p12 时设的密码 |
| Key alias | 创建时的别名 |
| Key password | 同上 |
| **Profile file (.p7b)** | `E:\zhixue-signing\zhixue-release.p7b` |
| **Certpath file (.cer)** | `E:\zhixue-signing\zhixue-release.cer` |

3. OK 保存 → DevEco 写入 `app/build-profile.json5` 的 `signingConfigs`
4. 确认 `products[0].signingConfig` 指向 `"release"`（当前是悬空的 `"default"`）
5. **Build → Build Hap(s)/APP(s) → Build Hap(s)**

### 若报"证书不匹配"

说明 DevEco 取了链里的 `[0]`（leaf）而不是 `[2]`。处理办法：

1. 把链中 SKI 为 `6F62...8CB9` 的那张单独导出成 `.cer` 再试
   （本目录下 `release-root.pem` 就是它，改扩展名为 `.cer` 即可）
2. 或者回 AGC 重新下载发布证书，确认下载的是 Profile 所绑定的那张

## 五、密钥库实测结果（第二轮，已解锁）

拿到密钥库口令后，用 DevEco 自带 JBR 的 `keytool` 读出：

```
Keystore type: PKCS12
Your keystore contains 1 entry

Alias name: zhixue-debug
Creation date: Sep 21, 2026
Entry type: PrivateKeyEntry
Certificate chain length: 1
Subject Public Key Algorithm: 256-bit EC (secp256r1) key
Signature algorithm name: SHA256withECDSA
Valid from: 2026-09-21 until: 2051-09-15

SubjectKeyIdentifier: 6F:62:09:DF:2D:14:95:A0:4D:2F:88:CB:E8:98:16:B1:06:14:8C:B9
```

### ★ 决定性发现：私钥与 Profile 配对闭合

| 来源 | SPKI sha256 | SKI |
|---|---|---|
| `.p12` 内**私钥**对应公钥 | `36:EC:7B:02:00:D8:4F:86:...:8D:04:B8` | — |
| `.p12` 内嵌证书 | `36:EC:7B:02:00:D8:4F:86:...:8D:04:B8` | `6F62...8CB9` |
| **Profile 内嵌证书** | **`36:EC:7B:02:00:D8:4F:86:...:8D:04:B8`** | **`6F62...8CB9`** |

**三者完全一致** —— 私钥、keystore 证书、Profile 绑定证书是同一密钥对。

> 这一条把 §五（旧版）里"`.p12` 私钥对应哪张证书未核验"的空白补上了，也让 §三 的兜底方案不再需要。

### 另一个困惑的解答

**keystore 里只有 1 张证书（自签，`CN=zhixue-debug`）**，而下载的 `.cer` 是 3 段链。

这解释了之前"leaf 与 root 公钥不一致"的现象：`.cer` 里的 `[2]` 才是 AGC 用它签发的那张（与 Profile 配对），`[0]` 是另一张。之前 AGC 界面显示的 `0B:6B:65:ED:...:7C:D3` 指纹与三者都不同，可能来自更早申请时产生的证书，现已不影响结论。

## 六、DevEco 手动签名参数（已核验，可直接照填）

