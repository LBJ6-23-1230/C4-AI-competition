## 3. 逐项详解

### 3.1 （问题 a）通知权限：**你的假设不成立，代码是对的**

**结论：`notificationManager.publish()` 不需要在 `module.json5` 里声明任何权限。缺少声明不会导致运行时失败。**

**证据链：**

1. **SDK 声明文件本身没有 `@permission` 标注。**
   在编译实际使用的 API 24 SDK 中，`notificationManager.publish` 的两个重载的 JSDoc 里
   **完全没有 `@permission` 标签**，也没有 `@systemapi` 标签：

   ```
   // D:\DevEco\DevEco Studio\sdk\default\openharmony\ets\api\@ohos.notificationManager.d.ts
   126:    function publish(request: NotificationRequest, callback: AsyncCallback<void>): void;
   193:    function publish(request: NotificationRequest): Promise<void>;
   ```
   其 `@throws` 列表里与权限相关的只有两条，都是**用户侧开关状态**而非应用侧权限声明：
   ```
   * @throws { BusinessError } 1600004 - Notification disabled.
   * @throws { BusinessError } 1600020 - The application is not allowed to send notifications due to permission settings.
   * @throws { BusinessError } 1600014 - No permission.
   ```
   `1600004 / 1600020` 的语义是"用户在系统设置里没给这个应用开通知授权"，而不是"你没在 module.json5 里写权限"。
   `1600014 No permission` 在该文件里附属于系统级 API（如 `cancel` 指定他人通知等），不是 `publish` 的常规路径。

2. **`ohos.permission.NOTIFICATION_CONTROLLER` 是系统应用权限，第三方应用申请不到，而且它管的是"代发/管理他人通知"，与本场景无关。**
   网上大量"怎么获取 NOTIFICATION_CONTROLLER 权限"的提问本身就是误解；该权限为 system_core 级，普通应用不在可申请名单内。

3. **工程实际采用的正是官方推荐路径**——先查开关、再弹系统授权框：
   ```ts
   // ProactiveSurfaceService.ets:46-50
   const enabled: boolean = await notificationManager.isNotificationEnabled();
   if (!enabled) {
     hilog.warn(DOMAIN, TAG, '%{public}s', 'Notification permission is disabled; skip publish.');
     return;
   }
   ```
   ```ts
   // ProactiveSurfaceService.ets:63-72
   static async requestPermission(context: common.UIAbilityContext): Promise<boolean> {
     try {
       if (await notificationManager.isNotificationEnabled()) return true;
       await notificationManager.requestEnableNotification(context);
       return await notificationManager.isNotificationEnabled();
     } catch (error) { ... return false; }
   }
   ```
   并有真实的 UI 触发点：`pages/Account.ets:68`
   ```ts
   const granted: boolean = await ProactiveSurfaceService.requestPermission(this.context());
   ```

4. **`requestEnableNotification(context)` 需 `UIAbilityContext` + `@StageModelOnly`**（SDK 中该重载带 `@StageModelOnly` 标注，API 12 起废弃无参重载）。
   工程传的就是 `common.UIAbilityContext`，用法正确，且本工程是 Stage 模型，约束满足。

**给评委/老师的一句话口径**：通知不需要在 `module.json5` 申请权限，只需要在首次使用时调用 `requestEnableNotification` 拉起系统授权弹窗；本项目已闭环实现，且在未授权时优雅跳过而非崩溃。

**唯一遗留问题**是使用了废弃字段（见 **D-1**），以及 `Account.ets:68` 的返回值 `granted` 似乎未被用于 UI 提示（需实机确认交互反馈是否可见）。

| `uiSyntax: "arkts"` | 声明为 ArkTS 卡片 | ✅ 正确，与 `LearningCard.ets` 用声明式 UI 一致 |
| `window.designWidth: 720` + `autoDesignWidth: true` | 与模板**逐字一致** | ✅ 正确 |
| `colorMode: "auto"` | 深浅色自适应 | ✅ 正确 |
| `isDefault: true` | 默认卡片 | ✅ 正确 |

### 3.5 （问题 e）Preferences：**线程安全没问题，异常处理规范；只有一个真实的隐私缺口**

**结论：全部使用同步 API（`getPreferencesSync` / `getSync` / `putSync` / `deleteSync` / `flushSync`），不存在并发写竞争；异常处理覆盖到位。但登录 token 明文落盘是真实风险。**

**统计**：6 个 Store 类，7 组 store 名，全部为**同步调用**，无一处使用异步 `getPreferences()` / `put()` / `flush()`。

**为什么同步 API 反而更安全**：ArkTS 的 `preferences` 异步 API 在多次快速 `put` 时存在回调顺序不确定的问题；
同步 API 在调用线程上串行执行，天然避免写-写交错。工程统一使用同步 API，是**正确的选择**。

**异常处理逐类核对：**

| Store | 读路径 | 写路径 | 判定 |
|---|---|---|---|
| `ApiEnvironmentStore` | `:15-21` try/catch | `:31-37` try/catch + `flushSync` | ✅ |
| `AuthStore` | `:29-46` try/catch，失败置 `session = null` 并 `return false` | `:98-119` try/catch + `flushSync` | ✅ |
| `FixtureDemoStateStore` | `:18-24` try/catch | `:65-72` try/catch + `flushSync` | ✅ |
| `WorkflowSessionStore` | `:17-30` try/catch | `:41-49` try/catch + `flushSync` | ✅ |
| `LearningCardService` | `:46-56` try/catch，失败回落 `defaultData()` | `:76-84` try/catch（含 `hilog.error`）+ `flushSync` | ✅ **最佳** |
| `ProactiveSettingsStore` | `:12-18` try/catch，失败置 `false`（保守关闭） | `:28-34` try/catch + `flushSync` | ✅ |

**优秀实践举例**（`LearningCardService.ets:44-57`）——读失败不抛错、不返回半成品，而是回落到完整默认值：
```ts
static read(context: common.Context): LearningCardData {
  try {
    const store: preferences.Preferences = preferences.getPreferencesSync(context, { name: ... });
    const raw: string = store.getSync(LearningCardService.KEY_DATA, '') as string;
    if (raw.length === 0) return LearningCardService.defaultData();
    const parsed: LearningCardData = JSON.parse(raw) as LearningCardData;
    return parsed.taskName.length > 0 ? parsed : LearningCardService.defaultData();
  } catch (error) {
    hilog.warn(DOMAIN, TAG, '%{public}s', `Read card snapshot failed: ${JSON.stringify(error)}`);
    return LearningCardService.defaultData();
  }
}
```
注意 `parsed.taskName.length > 0` 这个**结构合法性校验**：`JSON.parse` 成功不代表数据结构正确，
旧版本快照缺字段时这里会因 `taskName` 为 `undefined` 抛错，然后被 catch 兜住回落到默认值。**逻辑是自洽的。**

**唯一的真实缺口（非线程安全，是隐私与健壮性）**：
- **token 明文落盘**：`AuthStore.ets:112` `store.putSync(AuthStore.KEY_TOKEN, session.token)`。
  preferences 是**明文**存储（应用沙箱内，但 root / 备份可读）。
- **`AuthProvider` 的类型断言不安全**：`AuthStore.ets:44`
  ```ts

  ```
  当存量数据里的值不在 `AuthProvider` 联合类型内时，这个 `as` 会**掩盖**非法值，
  与同文件 `LearningCardService` 的结构校验风格不一致。（见 D-3）

- 但 `@deprecated since 11` + `@useinstead` 意味着**运行时实现已切到 `notificationContentType`**。

**为什么这不是"编译不过"**：ArkTS 的类型检查器对 `interface` 上的可选废弃字段不做拒绝，
`@deprecated` 只产生 IDE 提示，不产生编译错误。工程 0 error 也印证了这一点。

**稳妥改法**（不改也能编译，改了更保险——见 D-1）。

#### 3.7.3 关于报告中"从未编译"这一说法的处理建议

建议**彻底放弃"从未编译"这个表述**。原因：
- 它不成立，且`entry-default-unsigned.hap` 就在工程目录里，评委只要打开 DevEco 点一下 Build 就能证伪；
- 更严重的是，它会把一个**真实的优势**（"工程可编译、可产出 HAP、ArkTS 严格模式零错误"）
  说成劣势。这是白送分的地方被自己抹掉。

**注意区分两个不同的事实**（答辩时容易被追问）：
- ✅ **能编译**：`Debug` 模式构建通过，产出未签名 HAP。
- ⚠️ **未签名、未装机**：`build-profile.json5:3` 的 `"signingConfigs": []` 为空数组，
  构建日志有 `No signingConfig found, initRemoteHspCache failed.`，
  产物是 `entry-default-unsigned.hap`，**没有 `entry-default-signed.hap`**。
  另外产物目录里没有独立的 widget HAP（卡片随主 HAP 一起打包，符合预期）。
  → 即"**编译通过 ≠ 装到真机能跑**"。当前状态是编译通过、未签名、**装机与真机运行未验证**。

### D-2【高】语音引擎的 `online` 参数语义写反

- **现象**：`VoiceInputService.ets:113-116` 传 `online: 1`，代码意图是联网识别。
- **证据**：SDK `@hms.ai.speechRecognizer.d.ts:269-276`：
  ```
  * Indicates module type of the recognition.
  * The value 0 indicates online, value 1 indicates offline.
  online: number;
  ```
  → `online: 1` 实际选择**离线引擎**。
- **影响**：
  1. 离线引擎依赖设备本地语言包，**模拟器与部分真机可能不可用**（SDK 亦列出 `1002200001 - Create engine failed`），
     导致语音功能在答辩现场直接失败；
  2. 离线识别准确率通常低于联网，演示体验打折；
  3. 工程未做能力探测，失败时文案笼统（`readableError` 一律回落"当前设备无法启动语音识别"），
     难以现场判断是"没语言包"还是"没权限"。
- **建议改法**：改为 `online: 1` → **`online: 0`**（联网）；同时增加能力探测与显式降级：
  ```ts
  // 启动前探测支持的语言/模式
  const engine = await speechRecognizer.createEngine({ language: 'zh-CN', online: 0 });
  const languages: string[] = await engine.listLanguages({ sessionId: this.sessionId });
  if (languages.length === 0) { callbacks.onError('当前设备语音识别不可用，请直接输入文字。'); return; }
  ```
  并保留"识别失败→回退文字输入"的现有降级（这部分已经做得很好）。

### D-3【高】登录 token 明文落盘，且 `AuthProvider` 断言不安全

- **现象**：
  - `AuthStore.ets:112` `store.putSync(AuthStore.KEY_TOKEN, session.token);` —— token 明文写入 preferences。
  - `AuthStore.ets:44` `authProvider: store.getSync(AuthStore.KEY_PROVIDER, 'local') as AuthProvider,`

    const rawProvider: string = store.getSync(AuthStore.KEY_PROVIDER, 'local') as string;

  `ProactiveSurfaceService.publish` 全链路均无测试。
- **建议改法**：优先补 3 个用例（成本低、答辩可展示）：
  ① `LearningCardService.registerForm/unregisterForm` 的注册去重与移除；
  ② `LearningCardService.fromDecision` 对 `durationMinutes` 缺省时的兜底；

### D-12【低】`postCardAction` 传入的 `targetPage` 从未被消费

### 5.2 该用而未用 —— 按性价比排序

#### ★★★ 强烈建议补（1–3 天可完成，直接提升"鸿蒙深度"评分）

**（1）WantAgent 通知深链**
- 现状：通知无 `wantAgent`（D-7），点击只到首页。
- 为什么该用：这是 Notification Kit 的**标准用法**，缺了等于通知只做了一半；
  而且卡片链路已经有现成的参数协议（`source`/`taskName`/`durationMinutes`），**复用零成本**。
- 落地建议：见 D-7 代码片段。同步给 `Account.ets` 的授权结果加 UI 反馈。
- 答辩话术：「**卡片和通知是我们两条主动触达通道，都通过统一的 `Want.parameters` 协议把 Agent 决策带进应用，
  用户点一下就落到专注页，不需要在应用里找。**」

**（2）实况窗 / 通知模板升级（Live View）**
- 现状：`NOTIFICATION_CONTENT_SYSTEM_LIVE_VIEW` 未使用；通知只有基础文本。
- 为什么该用：本作品有**专注计时（FocusTimer）**这一天然适合实况窗的场景——
  番茄钟进行中在状态栏/锁屏常驻显示剩余时间，是"主动助学"最直观的体现。
- 落地建议：`FocusTimer` 启动时发一条 `NOTIFICATION_CONTENT_SYSTEM_LIVE_VIEW` 通知，
  每秒/每分更新 `NotificationSystemLiveViewContent`（capsule + time + progress），
  结束后 `cancel(notificationId)`。SDK 中 `NotificationSystemLiveViewContent` 位于
  `notificationContent.d.ts:266`，`NotificationCapsule:315`、`NotificationTime:381`、`NotificationProgress:422` 均已就绪。
- 答辩话术：「**专注不是后台挂着，而是通过实况窗变成系统的第一等公民——锁屏就能看到还有多久。**」
- 难度：中（需真机验证样式）。

**（3）意图框架（Insight Intent）**
- 现状：0 处使用。
- 为什么该用：**鸿蒙赛道 Agent 方向最对口的能力**。意图框架让"小艺"能直接调起本应用的能力，
  这是"Agent 与系统级入口打通"的唯一途径，也是"主动助学"从"应用内主动"升级为"系统级主动"的关键。
- 落地建议：至少注册 1–2 个意图，如：
  - `StartFocus`（参数：`taskName`、`durationMinutes`）—— 对应用户说"小艺，开始专注 30 分钟"；
  - `QueryTodayPlan` —— 对应"小艺，我今天该学什么"。
  已有 `EntryAbility.prepareLearningCardLaunch` 的参数协议可直接复用。
- 答辩话术：「**我们把 Agent 的核心动作注册成了系统意图，用户不打开应用也能触发，
  这才是鸿蒙意义上的全场景主动服务。**」
- 难度：中低（以配置为主）。**这是我认为当前"投入产出比最高"的一项。**

#### ★★ 建议补（视时间而定，能显著改善"全场景"叙事）

**（4）分布式/跨设备协同 —— 作品名的最大缺口**

- 现状：**"全场景"是作品名的核心词，但代码里 0 处分布式能力**。
  更值得注意的是，工程里有一个"**学习搭子匹配**"功能（`pages/PartnerMatch.ets`、`AgentBridge.ets:295-298`），
  它**天然就是多用户/多设备场景**，却完全靠后端 HTTP 模拟，没有用到任何鸿蒙分布式特性。
- 为什么该用：
  1. 评委看到"全场景"必然追问"哪里体现了全场景"，目前**答不上来**——这是最大的答辩风险点；
  2. 分布式软总线 / 分布式数据对象恰好能支撑"学习搭子共学"：两台设备间实时同步计时进度、互相可见学习状态。
- 落地建议（按成本从低到高）：
  - **最低成本（0.5 天，纯话术补强）**：明确定位为"**面向全场景设备形态设计**"——
    解释 `deviceTypes: ["phone"]` 为何当前只开手机（聚焦，
    并把 `supportDimensions: ["2*2","2*4"]` 的**双尺寸卡片适配**作为"已为多形态做准备"的证据。
    同时**坦诚说明**分布式协同在路线图上、尚未实现。诚实远好过被拆穿。
  - **中成本（3–5 天，真做）**：用 `distributedDataObject` 实现"学习搭子共学"——
    双设备实时同步专注计时与今日任务，一方开始专注另一方能看到。这是**真正能讲"全场景"的最小闭环**。
  - **高成本**：`continueTask` 跨端迁移（手机开始 → 平板继续）。
- 答辩话术（中成本版）：「**学习搭子不是一个后端匹配列表，而是两台设备之间通过分布式数据对象
  实时同步的学习场——你在手机上开始专注，你的搭子在平板上能看到你正在学什么。**」

**（5）端侧 AI / VisionKit —— 让"AI 创意赛"的 AI 落在端侧**

- 现状：`@kit.MindSporeLiteKit`、`@kit.CoreVisionKit` 均 0 处使用。
  当前所有 AI 都在 Flask 后端（`server/`），前端只是 HTTP 客户端 + 本地关键词匹配
  （`AgentBridge.matchIntentLocal`，`:22-33` 的规则表）。
- 为什么该用：
  1. 这是**人工智能创意赛**，评委可能问"AI 在哪里"。
     如果答案是"在服务器上"，则鸿蒙端只是个 UI，与赛道"鸿蒙特性"评分点结合不紧；
  2. 工程已有**错题拍照**场景（`ChatMain.ets:715-736`、`WrongQuestion.ets:57-59`），
     当前只是把图片 URI 传给后端。用 VisionKit 端侧 OCR 可以做到**离线也能识别题目文字**。
- 落地建议：
  - 端侧 OCR：用 `@kit.CoreVisionKit` 的 `textRecognition` 对错题图先做本地文字提取，
    再决定是否上传（**兼顾隐私与离线可用**）；
  - 端侧意图分类：把 `AgentBridge.matchIntentLocal` 的关键词规则升级为 MindSpore Lite 轻量模型，
    让"意图识别"这一步真正端侧化；
  - 更好的叙事：**"端侧小模型做意图路由 + 云端大模型做深度推理"的混合架构**——
    既省流量又保护隐私，且**正好对应鸿蒙"端云协同"的官方叙事**。
- 答辩话术：「**我们的 Agent 是端云协同的：简单意图、错题 OCR 在手机上端侧完成，
  需要深度推理才上云。这既保护了学生隐私，也让弱网环境下核心功能可用。**」
- 难度：中高（需模型转换与适配）。**若时间紧张，只做 VisionKit OCR 这一项即可，收益/成本比最好。**

**（6）后台任务（专注计时保活）**
- 现状：`backgroundTaskManager` / `KEEP_BACKGROUND_RUNNING` 0 处使用。
- 为什么该用：`FocusTimer` 是长时任务，若用户切到后台，计时是否继续？当前**未做保活处理**（需真机验证行为）。

- 答辩话术：「**专注计时走的是系统长时任务，切后台不会断，配合实况窗锁屏可见。**」

### 6.2 现有特性中最能成为答辩亮点的（按推荐优先级）

**亮点 1：桌面服务卡片 —— 完整闭环（★★★ 首要亮点）**

这是全项目**最有说服力**的鸿蒙特性，因为它不是"放了张卡片"，而是打通了四个环节：
```
Agent 决策（后端 /api/v1/agent/proactive）
   ↓ ProactiveSurfaceService.ets:37
本地快照持久化（preferences）           LearningCardService.ets:76-84
   ↓ 主动推送
formProvider.updateForm                LearningCardService.ets:116,128
   ↓ 用户点击
postCardAction(router) + Want.parameters  LearningCard.ets:15-26
   ↓
EntryAbility 解析参数 → 直达专注页       EntryAbility.ets:56-57, 142-160
```
**并且做对了一个最容易被忽略的架构决策**：卡片不做网络请求，只渲染本地快照
（`LearningCardService.ets:26-27` 的注释明确写了这个理由）。
双尺寸（2\*2 / 2\*4）也做了真实的 UI 分支适配，不是摆设。

**建议讲法**：
> 「服务卡片对我们不是装饰，是 Agent 的**常驻入口**。用户不需要打开 App，
> 桌面上就直接显示 Agent 算出来的下一个动作——学什么、学多久、为什么。
> 点一下卡片，参数通过 `Want` 带进 Ability，直接落到专注页，不需要在应用里翻菜单。
> 这里有个我们特意做的设计：**卡片不做任何网络请求**，因为 FormExtensionAbility 生命周期很短，
> 网络请求会被系统回收；所以我们把 Agent 决策持久化成本地快照，卡片只读快照。
> 另外 2×2 和 2×4 两种尺寸做了不同的信息密度——2×2 只留任务和时长，2×4 才展开推荐理由。」

**亮点 2：离线/联机双通道 + 现场容错（★★★ 答辩保险）**

`AgentApiClient.ets:131` + `ApiEnvironment.ets` + `ApiEnvironmentStore` 构成了
"一键切换真后端 / 离线 Fixture"的能力，默认走真后端（`ApiDefaults.ets:41` `DEFAULT_USE_FIXTURE = false`）。

**建议讲法**：
> 「我们的默认配置是**真跑后端 LLM**，不是录播。但考虑到比赛现场网络不可控，
> 我们做了 Fixture 离线通道和界面开关——**万一网络出问题，一键切换，演示链路不会断**。
> 同时我们保留了 4 个能被学生自己验证的离线场景（`server/` 里预置的演示数据）。」
>
> 这个点非常讨评委喜欢：**它证明你考虑过现场风险**。

**亮点 3：功能完整的语音输入 + 资源管理（★★ 技术细节亮点）**

不吹"用了 AI 语音"，而是讲**工程细节**，反而更可信：
- 自建 `AudioCapturer`（16k/单声道/S16LE）→ 按 640/1280 字节切帧 → `writeAudio`，
  因为 CoreSpeechKit 只吃 PCM 帧、不自己开麦（`VoiceInputService.ets:23-25` 注释写得清楚）；
- `isBusy()` 防重入、15 秒兜底 `setTimeout`、`off('readData')`→`stop()`→`release()` 的严格释放顺序；
- 权限被拒 / 引擎不可用 / 服务忙各有不同文案，**且始终保留文字输入作为降级**
  （`ChatMain.ets:684-690`、`VoiceInputService.ets:185-198`）。

**建议讲法**：
> 「语音这块我们踩了一个坑值得讲：**CoreSpeechKit 不会自己开麦克风，它只接受 PCM 音频帧**。
> 所以我们自己起 `AudioCapturer`，按识别引擎要求的帧长切分后喂进去，
> 并且严格管理两个生命周期——引擎在页面存活期间复用，麦克风每一轮用完立刻释放。
> 任何一步失败都会回退到文字输入，**不让用户卡住**。」

**亮点 4：诚实标注的架构决策（★★ 加分的软实力）**

### 6.4 给答辩的"三句话"框架

**第一句（定位，强调真实性）**
> 「知学 Mate 不是一个套壳应用。桌面服务卡片、系统通知、语音识别、数据持久化这四条鸿蒙能力线，
> 都是真实调用的系统 API，权限和生命周期都闭环——**工程 Debug 构建 0 error，ArkTS 严格模式下没有一处 `any`。**」

**第二句（亮点，强调深度）**
> 「最能说明问题的是**服务卡片**：Agent 在后端算出"下一步该做什么"，
> 我们把决策持久化成本地快照，通过 `formProvider.updateForm` 推到桌面卡片上——
> **卡片刻意不做网络请求**，因为 FormExtensionAbility 生命周期短、网络会被回收，这是鸿蒙卡片的硬约束。
> 用户点卡片，参数通过 `Want` 带进 Ability，直接落到专注页。
> 2×2 和 2×4 两种尺寸还做了不同的信息密度适配。」

**第三句（诚实，化解"全场景"追问）**
> 「需要坦诚说明的是：**"全场景"目前体现在设备形态设计上，不在分布式协同上。**
> 我们当前只开了手机（`deviceTypes: ["phone"]`），卡片已经做了 2×2 / 2×4 双尺寸适配，
> 是为折叠屏和平板做的准备。真正的跨设备学习状态同步——
> 比如学习搭子之间通过 `distributedDataObject` 实时互见学习进度——
> **在我们的路线图上，但这一版还没实现。**」
>
> 补充进攻性的一句（如果 P2 的意图框架做了）：
> 「不过我们已经在**意图框架**上做了一步：把"开始专注"和"查今日计划"注册成了系统意图，
> 用户对小艺说一句话就能触发 Agent，**不用打开应用**——这是我们认为比"堆分布式"更务实的一步。」

**为什么第三句要这样说**：鸿蒙赛道的评委几乎必然追问"全场景在哪里"。
主动承认边界 + 给出具体路线图 + 展示一个已落地的替代方案（意图框架），
**比含糊其辞或临时硬凑一个假 demo 得分高得多**。

### 6.5 结论

| | |
|---|---|
| **是否硬凑鸿蒙特性？** | **不是。** 所选能力与"主动助学 Agent"命题高度自洽，且全部真实调用 |
| **是否只是普通 App 换壳？** | **基本不是，但有一条边界。** 服务卡片 + 系统通知确实把 Agent 从"应用内"推到了"桌面/系统层"，这是鸿蒙独有的价值；但分布式、意图框架、端侧 AI 的缺失，使"全场景"目前仍是产品叙事而非技术事实 |
| **最需要补的** | ① 真机跑通 + 录屏；② 通知 `wantAgent` 深链；③ `online` 参数修正；④ 意图框架（性价比最高）；⑤ "全场景"的诚实话术 |
| **最不该做的** | 为了凑数量而硬上分布式软总线 / Push / AVSession 等与命题无关或无法讲透的能力 |
