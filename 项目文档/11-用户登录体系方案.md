## 一、直接回答：现在**能注册**，但**不能登录**

我实跑后端接口验证过（非代码推断）。准确结论：

| 能力 | 现状 | 证据 |
|---|---|---|
| 昵称注册 | ✅ **能用** | `POST /auth/register` → 201 + userId + token |
| 会话保持 | ✅ **能用** | token 存 preferences，重启后 `/auth/me` 通过 |
| **按昵称登录** | ❌ **原来不存在** | 前端 `AuthClient` **只有 `register()`，没有 `login()`** |
| **密码登录** | ❌ **刻意不做** | 后端 `auth/service.py` 文件头：自建密码存储是负担与合规风险 |
| 手机号 / 验证码 | ❌ **未实现** | 登录页点"验证码登录"直接提示"当前未接入" |
| 找回账号 | ❌ **不可能** | 没有任何"按昵称/手机号查账号"的接口 |

### 最致命的实测现象

```
第 1 次注册「张三」→ HTTP 201  userId = u-90d772159260
第 2 次注册「张三」→ HTTP 201  userId = u-969c6593237f     ← 又建了一个！
```

**用户以为自己"登录"了，实际上服务器上多了一个账号，旧画像永远读不到。**

原因是登录页两个标签（登录 / 注册）**在代码里都只调 `register()`**：

```typescript
// 修复前 Login.ets:139 —— 不管 mode 是 login 还是 register，都调 register
const result: AuthResult = await AuthClient.register(this.nickname, this.grade);
```

### 换设备 = 永久失去账号

原 `/auth/login` 需要 `userId + token`，而 token 只存在**原设备的 preferences** 里：

```
设备 A：注册 → token 存本地 → 一直能用
设备 B：只有昵称 → 无任何接口能登回 → 只能再注册一个新账号
清了应用数据：同上，账号永久失去
```

## 二、你说的按钮 bug：核实结果（比表面更深）

我逐行查了 `Login.ets`。分两层说：

### 第一层：文案本身写对了，但**动作是错的**（已修）

```typescript
// Login.ets:283（修复前）
Button(this.busy ? '处理中…' : (this.mode === 'login' ? '登录  →' : '注册并进入  →'))
```

这行的条件表达式**是对的**。但你观察到的现象是真的 —— 因为：

**两个标签下的动作完全相同（都调 `register`），所以"登录"这个按钮本质上就是"注册"。**
文案再对，行为也是错的。已修：现在按 `mode` 真正分派（见第三节）。

### 第二层：ArkTS `@Builder` 传参不保证刷新（已消除隐患）

原来的分段控件是**带参数**的 Builder：

```typescript
this.Segmented([{key:'login',...},{key:'register',...}], this.mode, (key) => {...})
```

ArkUI 的 `@Builder` 对**参数**采用**值传递**，参数不是可观察依赖，外层状态变化时
不保证重建 —— 这正是华为开发者社区反复出现的
"[@Builder 传参后 UI 不更新](https://developer.huawei.com/consumer/cn/doc/doccenter-dev-faq/faqs-arkui-1078)"
类问题（官方 FAQ：`@Builder` 装饰器参数传递有使用限制）。

**我没有真机，无法断言你是否正因此看到高亮/联动不刷新**，但这个写法本身有风险。
已改成**无参 Builder 直接读 `this.mode`**，依赖关系明确、必然刷新：

```typescript
this.ModeSegment()   // 内部直接读 this.mode，不接收参数
```

> 说明：`@Builder` 传参是否刷新取决于传入值的形式与 API 版本，
> 存在不刷新的已知情形。改成无参读 `this` 是**确定性更高**的写法，
> 属于"消除隐患"而非"确认修复了你的现象"。真机上请重点复验这一处。

## 四、⚠️ 必须说清的安全边界

**昵称不是秘密。** 所以"按昵称登录"**不是安全的认证方式**：

* 任何人输入你的昵称就能进入你的账号
* 它解决的是"同一昵称不该产生重复账号"这个**可用性**缺陷
* **不解决**身份校验

所以它只适合：**本地演示 / 单机使用 / 评委体验**。
真实多用户场景必须走第五节。

> 另外，前面审计还发现一个更严重的问题（**尚未修**）：
> 后端把 token 解析进 `g.current_user` 但**全项目 0 个端点读取它**，
> 前端画像页硬编码 `demo-user` —— 也就是说**登录了，看到的仍是演示账号的数据**。
> 这条不修，登录功能业务上是空的。详见 `docs/10` 缺陷 A。

## 五、真正意义上的用户登录还需要什么

### 5.1 需要建立的组件（按优先级）

| # | 组件 | 为什么必须 |
|---|---|---|
| 1 | **数据库**（见 §6） | JSON 文件无法支撑多用户并发与唯一约束 |
| 2 | **唯一身份标识** | 手机号唯一索引 —— 昵称做不到唯一 |
| 3 | **短信验证码服务** | 手机号方案的核心 |
| 4 | **验证码存储 + 限流** | 防刷、防爆破（Redis 或数据库表） |
| 5 | **凭据校验中间件** | 让 `g.current_user` 真正被端点使用 |
| 6 | **数据隔离** | 所有查询按 `userId` 过滤（当前是硬编码 demo-user） |

### 5.2 手机号验证码登录流程

```
① 用户输入手机号 → 点「获取验证码」
   ├─ 后端校验手机号格式（^1[3-9]\d{9}$）
   ├─ 限流检查：同号 60s 内只能发 1 次；同号/IP 每天 ≤10 次
   ├─ 生成 6 位数字验证码，**只存哈希**（不存明文）
   ├─ 存 Redis：key=code:{phone}  value=hash(code)  TTL=5min
   └─ 调短信服务商发送
        ├─ 阿里云短信 / 腾讯云短信 / 华为云短信
        └─ 若未配置短信服务 → 返回"开发模式验证码"并在响应里回显
           （**仅限开发环境**，生产必须关闭）

② 用户输入验证码 → 点「登录 / 注册」
   ├─ 取 code:{phone}，比对哈希
   ├─ 错误次数 ≥5 → 锁定该手机号 15 分钟
   ├─ 校验通过 → 删除验证码（一次性）
   └─ 查 users 表：
        ├─ 手机号已存在 → 登录（返回既有 userId + 新 token）
        └─ 手机号不存在 → 自动注册（创建 userId + starter profile）

③ 返回 {user, token, expiresAt, created}
```

**关键设计点**：

| 点 | 做法 | 理由 |
|---|---|---|
| 验证码只存哈希 | 存 `sha256(code + salt)` | 数据库泄露也无法直接使用 |
| 一次性消费 | 校验成功后立即删除 | 防重放 |
| 双重限流 | 60s/次 + 每天 10 次 | 防短信轰炸（**这是真实的钱**） |
| 错误锁定 | 5 次错误锁 15 分钟 | 防 6 位码爆破（10⁶ 空间） |
| 手机号脱敏 | 库里存明文但界面 `138****8888` | 已备好 `maskPhone()` 函数 |
| 自动注册 | 手机号不存在即建号 | 减少一步操作，业界标准做法（微信/美团） |

### 5.3 三方登录（可选，加分项）

华为鸿蒙项目有天然优势：**AGC 认证服务**（`@kit.AccountKit`）支持：

* 华为账号一键登录（`Authentication` / `HWAccount`）
* 手机号一键登录（运营商网关取号，**免验证码**，体验最好）
* 微信 / 微博等第三方

`auth/service.py` 里 `authProvider` 字段已经预留了
`'agc_phone' | 'agc_anonymous'` 取值 —— **架构上是接得上的**。

> 竞赛向建议：**答辩时讲"已预留 AGC 接入点 + authProvider 枚举已就位"**，
> 比"我们做了验证码"更能体现架构意识。真实接入 AGC 需要开发者认证，成本较高。

## 六、要不要数据库？——要，但不是"必须现在换"

### 6.1 现状：JSON 文件已经是瓶颈

当前用 `data/repository.json` 单文件存储，`JsonRepository._flush()` **每次保存全量重写整个文件**。

我实测到的问题：

| 问题 | 实测 |
|---|---|
| 无唯一约束 | 同名注册产生重复账号（**这正是本次登录缺陷的土壤**） |
| 无并发保护 | 8 并发写 **88% 返回 500**（已修：加锁 + 唯一临时名） |
| 全量重写 | 2.5MB 仓库时单次 save 需 **~30ms**，每次 `/run` 要 save 2–3 次 |
| 无索引 | 按昵称查账号要**全表扫描**（`find_users_by_nickname` 就是遍历） |
| 单文件锁 | 多进程不安全（审计实测双进程并发 500 率 5%–19%） |

**结论：JSON 适合单机演示，不适合多用户真实登录。**

### 6.2 选型建议

| 方案 | 适合 | 优点 | 缺点 |
|---|---|---|---|
| **SQLite** | 演示 / 单机 | 零运维、单文件、支持唯一索引与事务 | 写锁全库，不适合并发写 |
| **PostgreSQL** ⭐ | 真要上线 | 唯一约束、并发、全文检索、可扩展 pgvector 做 RAG | 要部署与运维 |
| **MySQL** | 团队熟悉时 | 生态成熟 | 同上 |
| Redis（附加） | 验证码 / 会话 | TTL 天然适合验证码与限流 | 需额外部署 |

**推荐路径（务实）**：

```
现在（复赛）      SQLite  —— 换取唯一约束 + 事务，几乎零成本
                     ↓
上线 / 国赛        PostgreSQL + Redis
                     ↓
③ 知识库 RAG       PostgreSQL + pgvector（同一套库直接加向量能力）
```

> **关键收益**：换成 SQLite 立刻能加 `UNIQUE(phone)` 与 `UNIQUE(nickname)`，
> 从**数据库层**根治"重复账号"——这比在应用层查重可靠得多。

### 6.3 不换数据库的过渡方案（如果时间实在不够）

给 JSON 仓库加**应用层唯一约束**：

```python
# 注册/登录前先查重（已有 find_users_by_nickname）
# 并在 nickname 上建立内存索引，避免全表扫描
```

**但必须承认**：这只是缓解。多进程并发下仍可能产生重复账号。
