## 1. 视频只讲一个故事

不要把视频拍成功能列表。全片围绕同一个学生、同一个薄弱点展开：

> 考试临近，不知道先学什么  
> → 使用准备好的参赛演示账号真实登录  
> → 一句话提出需求  
> → 画像与错题共同定位薄弱点  
> → 做三道专项练习  
> → 掌握度从 42 更新到 58  
> → 计划由 30/30 自动调整为 45/15  
> → 根据目标、时间和知识结构匹配学习搭子  
> → 进入专注并完成复盘  
> → 在另一台设备继续当前任务（仅在真机实测成功时展示）

评委最终需要记住的不是功能数量，而是这一句：

> **大模型负责理解与表达；判分、掌握度、优先级和重规划由可核对的确定性代码完成。**

## 2. 真实性边界

以下口径在录制和配音时必须统一。

| 能力 | 可以说 | 不能只凭什么就说 |
|---|---|---|
| 大模型调用 | 本次响应标注“大模型生成”，且响应元数据显示 `llmUsed=true` | 不能只凭后端出现 HTTP 200 就说模型调用成功 |
| 后端请求 | App 操作真实经过后端接口 | HTTP 200 只证明接口成功，不证明使用了模型 |
| 规则兜底 | 后端在线但模型不可用时，界面如实标注规则兜底 | 关闭整个后端只证明网络不可用，不等于规则兜底 |
| 确定性计算 | 相同输入得到相同判分、掌握度和计划结果 | 不说“今天和明天结果一定相同”，因为紧迫度可能随日期变化 |
| 跨设备接续 | 两台真机实际完成任务同步后，可以说“已实现并实测” | 两个模拟器各自加入会话，不能证明数据已经跨设备传递 |
| 小艺意图 | 真机口令成功拉起目标页后再展示 | 只有代码和注册配置时，不说已完成真机验证 |
| 语义检索 | 页面实际显示 `hybrid:semantic+keyword+tag` 时再说语义重排已生效 | 页面显示 `keyword+tag` 时不能包装成语义检索 |

### 2.1 证据强度排序

优先使用评委一眼能看懂的产品证据：

1. 用户操作后，界面结果发生可见变化。
2. 两台真实设备在同一镜头内完成状态接续。
3. 页面展示来源标签、因子贡献和状态版本。
4. 接口响应元数据或经过脱敏的后台状态。
5. 代码、终端日志、OpenAPI 文件只作为极短补充，不作为主要证明。

## 5. 可选补充素材

以下内容可以录制，但默认不进入 5 分钟主片。只有主线缺少相应评分证据时才替换进去。

### 是否需要展示后端？

**需要证明后端存在，但不需要专门讲解后端。** 推荐只在第 10 段插入一个 **3–5 秒**的脱敏画中画：左侧保留 App 的实际操作结果，右侧显示对应接口成功、`llmUsed` 或状态版本。评委首先看产品体验，终端窗口和代码不是主角。

后端镜头只承担两个任务：

1. 证明 App 不是纯静态页面或预录结果。
2. 补充页面不便呈现的来源元数据与状态版本。

不要在主片中现场启动服务、输入命令、滚动整份日志或打开大段源码。这些动作占时间，也容易暴露路径、IP、Token 或 Key。完整后端测试和契约检查可作为答辩备用材料，不必塞进演示视频。

### 5.1 后端与模型状态

建议画面：App 来源标签 + 脱敏后的响应元数据 `llmUsed=true` + 后端健康状态。

正确旁白：

> 本次请求真实经过后端；响应元数据和页面来源标签共同表明本次使用了大模型。

不要只展示 `POST /api/agent/chat 200` 就声称模型调用成功。

### 5.2 诚实降级

若要展示，使用“后端在线、模型调用失败”的可控测试场景：

1. 后端保持运行。
2. 使用测试开关或无效测试配置触发模型调用失败。
3. App 明确显示规则兜底，响应中 `llmUsed=false`。
4. 恢复配置后再次发送，显示大模型来源。

不要在主片中临时 Ctrl+C 停掉整个后端；那只能证明网络错误，而且容易破坏后续录制。

### 5.3 契约一致性

当前契约包含 **39 条路径、44 个操作、64 个 schema**，两份 `openapi.json` 可验证为逐字节一致。若展示，只保留 3–5 秒测试结果，不滚动整份 JSON。

### 5.4 知识库检索

- 页面显示 `hybrid:semantic+keyword+tag`：可以说语义与关键词混合检索已实际生效。
- 页面显示 `keyword+tag`：只说当前使用关键词与标签检索，并如实标注降级模式。

### 5.5 隐藏接口环境入口

不建议进入主片。它是开发调试细节，对创新性、完整性和落地价值的贡献有限。

## 6. 录制前一键预检

所有命令必须注明在哪种终端运行，避免混用 PowerShell 与 Git Bash。

### 6.1 先准备两个专用演示账号

正式视频既要真实登录，又要展示学习搭子，因此至少准备两个**只用于参赛演示**的账号：

| 账号 | 用途 | 录制前必须具备 |
|---|---|---|
| 主账号 A | 登录后完成整条主线 | 演示画像、V1 计划、三道题、目标、课程、空闲时间 |
| 候选账号 B | 被匹配并接收邀请 | 不同但互补的掌握度、相同课程目标、与 A 重叠的空闲时间 |

建议使用不含个人信息的昵称，例如“知学演示A”“知学演示B”，使用专用测试手机号和专用密码。密码输入镜头可保持掩码，不在字幕或旁白中公开。

**关键提醒：**`POST /api/v1/demo/reset` 只重置 `demo-user`。真实登录账号默认从空画像开始，因此不能指望执行该命令后，账号 A 自动拥有 42、V1 和 30/30。账号 A、B 必须提前完成一次初始化并保存，随后用专门的演示数据准备脚本或受控备份在每次彩排前恢复。

录制前至少完整验证一次：

1. A 能通过昵称 + 密码成功登录，并显示“欢迎回来”。
2. A 登录后能看到 42 和 V1 `[30,30]`。
3. A 做 A/B/A 后得到 66.67、42→58、V2 `[45,15]`。
4. A 的搭子页能匹配到 B，五因子不全为零。
5. A 发出的邀请能出现在 B 的收件箱；需要展示接受流程时，再由 B 接受。

## 10. 现场失败时的替换规则

| 失败情况 | 立即替换 |
|---|---|
| 大模型不稳定 | 使用此前录好的真实成功素材；不得伪造来源标签 |
| 错题识别失败 | 换清晰备用图；仍失败则使用明确标注的内置示例 |
| 数字偏离基线 | 恢复主账号 A 的受控演示数据，从练习段开始重录；不要用 demo reset 冒充真实账号重置 |
| 搭子页没有候选人 | 检查候选账号 B 的资料与服务端状态；不要切离线候选冒充真实账号 |
| 两个模拟器无法发现对端 | 属于当前模拟器架构限制；保留多形态适配镜头，不声称已完成跨端数据流动 |
| 小艺口令失败 | 删除该镜头，以服务卡片或大屏适配替换 |
| 语义检索降级 | 如实展示关键词模式，或从主片删除该段 |
| 后端意外中断 | 停止该素材包录制；恢复并自检后重录，不在主片展示事故 |

## 11. 最终原则

成片的优先级依次是：

1. **真实**：只说镜头能证明的内容。
2. **闭环**：每个功能都推动同一个学习任务向前。
3. **易懂**：先展示用户结果，再解释技术原因。
4. **鸿蒙特色**：优先展示真机、跨设备、服务卡片和大屏适配。
5. **技术深度**：用来源标签、因子贡献和状态版本证明，不用代码墙代替产品证据。

只要 `66.67 → 42→58 → V1→V2 → 30/30→45/15` 这一条因果链拍清楚，再加上一段经得起核验的鸿蒙能力，整支视频就已经有非常强的完整性和可信度。
